# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Forge" — a mobile-first (iOS-styled) workout generator and live-tracking web app. Despite the repo name (`gym-craft-ios`), this is **not native Swift** — it's a React 19 + TypeScript SPA/SSR app built with TanStack Start, Vite, and Tailwind CSS v4, run inside a browser/webview. Some files are Supabase codegen and are marked accordingly (see Architecture below).

## Commands

```sh
npm run dev       # start the Vite dev server
npm run build     # production build
npm run build:dev # build in development mode
npm run preview   # preview a production build
npm run lint      # eslint .
npm run format    # prettier --write .
```

There is no test suite configured (no test runner in devDependencies, no `test` script). Type-check with `npx tsc --noEmit`.

## Architecture

### Vite/TanStack Start config is pre-bundled

`vite.config.ts` wraps everything in `@lovable.dev/vite-tanstack-config`, which already registers TanStack Start, React, Tailwind, `vite-tsconfig-paths`, Nitro, the `@` path alias, and TanStack devtools. **Do not add these plugins again** — the file itself has a comment warning that duplicating them breaks the app. Only pass extra options via `defineConfig({ vite: { ... } })`.

### Routing

File-based routing via `@tanstack/react-router`'s Vite plugin: files under `src/routes/` become routes, and `src/routeTree.gen.ts` is generated from them — never hand-edit it (running `npm run dev` or `npm run build` regenerates it after adding/removing a route file; the plugin also auto-rewrites `createFileRoute("/…")`'s own path argument in a route file after a rename, so that string doesn't need to be hand-fixed either). `src/routes/__root.tsx` sets up the HTML shell, `QueryClientProvider`, the global `GymProvider`, and the floating `TabBar`. `TabBar` carries five tabs, in this order: `generate` (labeled "Workout" — the time/equipment/muscle workout generator, `index`'s original content before the Home dashboard took over `/`), `history` (+ `history.$workoutId`), `index` (the Home dashboard, see below) dead center, `exercises`, and `nutrition`. `equipment` isn't a tab at all — see below. `settings` (account/cloud-sync + appearance) is reachable from the profile icon in both `index`'s and `generate`'s header (`Screen`'s `action` slot) rather than from the `TabBar` — it's still globally reachable since `TabBar` renders on every route regardless.

**Home's tab is an ordinary inline cell again, not a detached raised circle.** The app went through two prior designs here: first a bigger flex share inside one continuous pill (`emphasize` flag), then — per an explicit reference image — a genuinely separate `size-16` circle `absolute`-positioned to float above the pill's own top edge (`top-3 -translate-y-1/2`), overlapping down into it. That second design was reported as wanting its vertical footprint back: raising the circle above the pill made the bar's combined visual height taller than a flat single-pill bar, which every scrollable route had to reserve extra bottom padding for. Home is now a plain `flex-1` cell in the same `LEFT_TABS`/`RIGHT_TABS` row as the other four (no more split pill halves, no `w-16` spacer, no `relative`/`absolute` positioning at all) — same `min-h-[54px]` row height as every other tab, so the bar's total footprint is exactly one row tall again. What still makes it read as the one emphasized action isn't its position or height anymore, it's purely the badge inside it: a circle, `bg-primary`/`text-primary-foreground` so it follows whichever accent is chosen in Settings like every other themed surface, always solid — never muted when you're not actually on `/`, unlike the other four tabs' icon-color-only active state. Sized via `h-full aspect-square` rather than a fixed `size-*` — `h-full` stretches it to exactly the row's own rendered height (54px) rather than sitting smaller inside it, and `aspect-square` locks the width to match that height 1:1, so `rounded-full` still produces a true circle (equal radius on every side) instead of an oval once the height changed; reported as wanting the badge to fill the bar's own height rather than float at a fixed smaller size within it. `<nav>`'s own top padding shrank back down alongside the circle's original repositioning (`pt-8` → `pt-2`, no longer needing extra clearance for a circle poking above the pill).

The other four tabs dropped their text labels entirely (icon-only now, `aria-label` carrying the accessible name screen readers need in place of visible text) and traded the old `bg-primary/15` active-pill background for a plain icon-color change (`text-primary` active / `text-muted-foreground` inactive) plus a small dot rendered below the icon — transparent when inactive, `bg-primary` when active, always present in the DOM either way so a tab switching active state never shifts the row's height. Matches the reference image's own language: flat icons, a small active-indicator dot, no per-tab background pill.

Each `TabButton`'s icon+dot cluster carries a `pt-3` on top of its `justify-center`, deliberately sitting it a few pixels below the row's own vertical center line rather than dead-centered — reported once Home's badge grew to fill the full row height (see below) that the other four icons, still their original size, read as floating noticeably higher than Home's now-larger, still-centered glyph. `pt-3` shifts the whole icon+dot group down as a unit (icon and dot both keep their exact prior size, `size-[22px]`/`size-1`) rather than resizing or restyling either — measured after the change: the icon+dot cluster's own visual center sits ~6px below the row's center line, with the dot still comfortably clear of the row's bottom edge.

Every scrollable route still reserves exact bottom padding sized to the bar's actual footprint (`pb-[calc(5.625rem+var(--tab-bar-clearance))]`, in both `Screen.tsx` and `index.tsx`) so its last card/button doesn't end up hidden behind it, both call sites referencing a shared `--tab-bar-content-clearance` custom property (`styles.css`, `:root`) instead of repeating the same literal twice. Dropping the raised circle shrank this from `7rem` down to `5.75rem` — re-measured the same way the original value was (actual `getBoundingClientRect()`s via Playwright, not eyeballed): the bar's own height dropped from a raised circle poking well above the pill to a flat one-row pill (`pt-8`→`pt-2` on top of that), freeing real vertical budget back to every route below it, `index.tsx`'s own fixed-height grid included. Re-verified scrolling `/history` to its true bottom leaves a clean ~28.5px gap between the last piece of content and the pill's own top edge, consistent across all three documented breakpoints (390×844, 402×874, 430×932) — and re-ran the Home dashboard's own 12-combination per-tile overflow matrix (see the real-device clipping writeup below) against the new, smaller clearance value, confirming zero real content overflow with the freed space. A single source of truth here specifically because it has to track `TabBar.tsx`'s actual layout by hand — letting `Screen.tsx` and `index.tsx` drift to different values would silently clip content on whichever routes kept the stale one. Content sitting partly behind the bar at the *initial*, unscrolled view of a taller-than-one-viewport route (e.g. `/nutrition`'s "Meals" section on first load) is expected and not a regression — that's true of any fixed bottom bar over normal-flow content that hasn't been scrolled yet; the actual invariant that matters, and the one this padding exists to guarantee, is that the content clears the bar once scrolled all the way down, verified directly via Playwright rather than inferred from the padding number alone.

`equipment` (gear/plate profiles, avoided exercises) used to be a sixth tab; it moved into a "Equipment profiles" row on `settings.tsx` instead (a plain `Link` styled like the other settings rows — icon badge, label/subtitle, trailing chevron — right after the Account card), on the reasoning that it's a setup screen visited rarely after a user's first session, not a daily destination worth a permanent slot in a five-item bar. The route itself (`/equipment`) is unchanged and still has no back action of its own, same as `settings` — both rely on the still-globally-rendered `TabBar` to navigate elsewhere. `index.tsx`'s own three-icon quick-links row (Equipment/Exercises/History, unrelated to the global `TabBar`) still links to it too — a second, redundant entry point is fine here, the same way `settings` is reachable from two different headers' profile icons.

### Home dashboard

`index.tsx` is a read-mostly overview screen — the first thing a cold app launch shows — rather than the workout generator that used to live at `/`. That generator (the full duration/equipment/muscle-map/plan-builder flow, `WorkoutHome`) moved to `generate.tsx` (`/generate`) unchanged; `index.tsx` is an entirely new component (`HomeScreen`) that reads the same `useGym()` state every other screen does but never mutates it — a summary with deep links out, not a new source of truth. Every action on it is a `navigate()` to some other route; nothing here calls a store action directly.

**Single fixed screen, deliberately not scrollable.** Unlike every other route (which uses the shared `Screen` component — a sticky header over a normally-flowing, scrollable `main`), `HomeScreen` renders its own `fixed inset-0 flex flex-col overflow-hidden` wrapper instead of `Screen`, with `main` itself `flex-1 min-h-0 overflow-hidden`. That combination is what makes "no scrolling" a real, enforced property rather than a sizing target to eyeball: `fixed` takes the page out of document flow entirely (so there's no `<body>` scroll to fall back on), and `overflow-hidden` on both layers means any content that somehow doesn't fit gets silently clipped rather than producing a scrollbar — the failure mode of getting this wrong is invisible content, not a broken layout, which is exactly why every piece of dynamic text below is wrapped in `truncate`. The bento tile grid (see below) uses a fractional `grid-rows-[...]` inside a `flex-1 min-h-0` parent, so its rows always split whatever vertical space is actually left after the header, hero and quick-links row in the same proportions regardless of device — it never needs device-specific pixel tuning and reflows correctly across the iPhone 14–17 Pro/Pro Max size range (verified via Playwright at 390×844, 402×874 — the iPhone 17 Pro's CSS-point size, unchanged from the 16 Pro's — and 430×932, checking both that `document.documentElement.scrollHeight` never exceeds `clientHeight` and that no element's bounding box extends past `window.innerHeight`, in both an empty fresh-install state and a fully-populated one). This same check gets re-run any time the row count or fractions change — the exact `grid-rows-[...]` value itself is documented where it's set, in "The stat grid" below, since it's changed more than once as tiles were added, resized or promoted.

**Layout, top to bottom:** a compact header (today's date, a time-of-day `greeting()` as the page's actual title instead of a literal "Home" — friendlier, and saves the vertical cost of a separate title *and* subtitle line — plus the profile-avatar settings button); one hero card; a bento grid of stat tiles (currently five rows — see "The stat grid" below for the exact tile lineup) that fills all remaining space; a three-icon quick-links row pinned just above the tab bar. There is no separate quick-actions row and no separate training-plan card — those were two of the original four-viewport-scrolls'-worth of stacked sections from the first version of this screen, and fitting everything into one fixed screen meant cutting hard rather than shrinking everything proportionally: the hero now carries both jobs at once (status *and* the one CTA that matters most), and **Saved templates**/**Last session**, which existed as their own full-width sections before, were dropped entirely — both remain one tap away (`/generate` lists saved templates, `/history` lists past sessions), and a dashboard that shows five sections well beats one that shows nine crammed thin.

**The hero** is a single `<button>` whose content is picked by priority, since there's only room for one dominant message: an in-progress `activeWorkout` always wins (resuming it is more urgent than anything else) — eyebrow "Session in progress", the set/exercise count, CTA "Resume" → `/session`; else an active `program` — eyebrow "Week N of M" (+ "· Deload" for a deload week), title "Next: {day}", a thin per-week progress strip (same data as `generate.tsx`'s own), CTA "Continue" → `/generate`; else a `weeklyScheme` — same shape without the week strip; else a bare "Ready to train?" prompt with CTA "Generate". The program-case subtitle dedupes `program.name` against the split template's own label (`program.name === templateLabel ? templateLabel : "${program.name} · ${templateLabel}"`) — since `ProgramBuilderSheet` defaults an unrenamed program's name to exactly the template's label, showing both unconditionally would read as a stutter ("Push / Pull / Legs · Push / Pull / Legs") for the common case of a user who never renamed it.

**The stat grid** is five rows on `grid-cols-2 grid-rows-[0.76fr_0.8fr_0.68fr_0.33fr_0.33fr]` (Nutrition / Water / Readiness / Activity / Best lift) — originally three rows with water folded into a small pill inside the Nutrition tile, but promoted to its own full-width row once water needed to be both bigger and directly actionable (see `WaterTile` below), which meant re-deriving every row's share of the same fixed vertical budget rather than just inserting a row for free. Readiness (see its own paragraph below) went through the same re-derivation a second time when it moved here from `/generate`. The tiles whose content has genuinely unpredictable width (nutrition's four numbers, a PR's exercise name) or that need room for a row of tap targets (water's quick-add buttons, readiness's emoji picker) get a full-width row (`col-span-2`) of their own rather than being forced into a square cell. All five tiles always render — none are conditionally hidden — specifically to keep the grid structurally stable; the empty states (`0`, "No PR yet", all-zero macros, "0L", an unanswered readiness picker) are themselves the fresh-install experience, verified via Playwright rather than assumed.

**Activity** (`ActivityTile`, full-width, between Readiness and Best lift) replaced what used to be two separate square tiles — Streak (`lib/gym/streak.ts`'s `currentStreak`, with `bestStreak` as a caption when it beats the current run) and This week (a plain 7-day session count with total as a caption) — sharing one row as half-width cells, each with its own icon badge, uppercase label, big tabular number, caption, and ghost-icon watermark. Reported as reading too cramped once the grid grew to five rows and every tile's padding got trimmed to fit real safe-area insets (see the real-device clipping writeup below): the fix wasn't more padding on tiles already at their minimum, it was needing fewer distinct stat blocks. Streak and This week are both single-number, low-detail stats that read fine side by side in one slim row — icon + number + caption, twice, split by a vertical divider — instead of two full square cells each carrying their own label row and ghost watermark (which only earns its keep on a tile tall enough to have real dead space to fill; `ActivityTile`, like `BestLiftTile` below, skips it). Both `to /history`, same as before. Merging them this way is what actually freed the row height the grid's *other* tiles needed back: measured directly, the two-cell version's row was rendering the grid cell at ~100-102px tall while the combined tile's actual content (icon circle + two text lines) only needed ~60px including its own padding — roughly 40px of pure slack that had been invisible to a check that only compared the outer document's scroll height, not what a stretched CSS Grid cell was doing to content shorter than its own row. That freed budget (plus shrinking Best lift's row to match Activity's new, much smaller share) is what let Nutrition/Water/Readiness's padding, gaps and touch-target sizes get restored past their real-device-clipping-fix minimums to something with actual room to breathe, re-verified via the same 12-combination Playwright check (three breakpoints × readiness state × program presence × data state) described below.

**Readiness** (`ReadinessTile`, full-width, between Water and Streak/This week) moved here from `/generate`'s own "Readiness" card — the check-in itself ("how are you feeling today?") is a whole-day question, not something specific to the workout generator, and belongs on the screen that's actually the app's daily landing point rather than a screen a user might not open every day. `/generate` still reads `readinessLog` directly (via `todaysCheckIn`) for its own suggestion math — only the interactive check-in widget moved, not the underlying data or its effect on `suggestWeight`'s `readinessWeightFactor`/`readinessNote` nudge (see "Progressive overload" below). Like `WaterTile`, this is the other Home tile that breaks `HomeScreen`'s own read-mostly rule and calls a store action directly (`setTodayReadiness`) rather than only navigating — the same "no extra taps" reasoning: a same-screen tap beats a trip to `/generate` and back for something meant to be answered once, first thing. Two states, unchanged in substance from the original `/generate` card: answered-and-not-editing collapses to a single centered row (icon badge, emoji + label, a "Change" pill that re-opens the picker); anything else (unanswered, or mid-edit) shows a 5-wide row of small emoji buttons instead, sized to fit within this tile's fixed grid-row height rather than the generator page's own unbounded vertical room.

**A real-device screenshot caught genuine clipping this Playwright methodology had missed, and exposed two real gaps in how "verified via Playwright" had been checked up to this point, not just in this feature.** The report showed several tiles' content cut off mid-line — the readiness picker's emoji row, the nutrition macro labels, "This week"'s "N total" caption — on an iPhone with an active program (so the hero renders its extra week-progress-strip row) and the readiness check-in still unanswered (the taller of its two states). Two independent causes, both structural rather than specific to this feature:

1. **Chromium doesn't populate `env(safe-area-inset-*)` the way a real notched/Dynamic-Island iPhone does.** `Screen.tsx`'s `safe-top` utility (and `--tab-bar-clearance`) reads `env(safe-area-inset-top/bottom)`, which resolves to a real ~59px/~34px on a Dynamic Island device in portrait but falls back to Chromium's own minimum (`0.75rem`/`1rem`) in every previous Playwright check here — a ~47px difference at the top alone that no earlier verification (this feature's included) ever accounted for, silently inflating how much vertical room those checks thought the page had. Reproducing this in Playwright needs an explicit `page.addStyleTag` overriding `.safe-top`'s `padding-top` and `--tab-bar-clearance` to the real device's values before measuring — there's no Chromium flag or device-emulation preset that fills this in automatically.
2. **A whole-document `scrollHeight > clientHeight` check (the one this file's own methodology has cited throughout the Home dashboard sections) cannot see per-tile clipping in a layout built on `overflow-hidden` boxes.** Each bento tile clips its own overflow by design (that's what makes the ghost-watermark-icon bleed safe) — so content that's too tall for its *own* tile's fixed grid-row height never makes the outer document taller at all; `document.documentElement` stays exactly viewport-sized either way. The real check has to walk each tile's actual content elements and compare against that tile's own bounding box, not the page's.

Fixed the layout by re-trimming padding/gaps across every bento tile (`p-3.5`→`p-3` or `p-2.5`, several internal `gap`/`py` values shaved further), the hero (`p-5`→`p-4`, its progress-strip margin tightened), `main`'s own top padding and inter-section gap, and the quick-links row's `min-h`, until the tallest realistic combination (active program + unanswered readiness + real Dynamic Island safe-area insets, at 390×844 — the smallest of the three documented breakpoints, and the one where this actually broke) has zero genuine content overflow. Re-verified across all three breakpoints, both readiness states, with and without an active program, and in both a fresh and a populated data state (12 combinations total) — this time with the safe-area override applied and a per-tile content check (excluding `pointer-events-none` ghost-icon descendants, which don't affect what's legible) rather than the document-level check. Any future change to this grid's row fractions or tile padding needs the same two corrections applied before trusting a "no overflow" result — a plain `document.documentElement.scrollHeight` check and a default Chromium viewport will both pass even when a real Dynamic-Island device is visibly clipping content.

**Icon badges are solid-fill, not tinted.** Every small circular icon badge on this screen (`NutritionTile`'s calorie-line icon, `BestLiftTile`'s trophy icon, `ActivityTile`'s two icon badges for Streak/This week) and every pill (`BestLiftTile`'s `{e1rm} kg` pill, `WaterTile`'s four quick-add buttons) uses `bg-primary text-primary-foreground` when active/populated — a solid, filled circle or pill with a foreground-colored icon or number, exactly the same treatment `TabBar`'s raised Home circle and the hero's own CTA button (`bg-primary`/`text-primary-foreground`) already used. These started out as a lighter `bg-primary/15 text-primary` tint (a translucent color wash with a colored icon on top) — legible enough in isolation, but inconsistent against the screen's two already-solid `bg-primary` elements, and reported as wanting the same crisp, "lit up" look those already had, especially once light mode (see the "Light/dark/system color scheme" section) made the difference between a solid badge and a washed-out tinted one more visible against a light card. `text-primary-foreground` (not a literal white) is what actually makes this correct across accents — it resolves to near-white on `blue`/`purple`/`pink`/`custom`, but stays a dark, near-black tone on `green`/`orange`/`yellow`, whose bright, high-lightness `--primary` needs a dark foreground for contrast; hardcoding white would have broken exactly those three accents. The inactive/empty state (`bg-muted text-muted-foreground`) is unchanged — this is purely about how a badge looks once it has something to show. Not extended to every `bg-primary/15`-style element app-wide in this pass — `settings.tsx`'s Equipment-profiles row icon, `exercises.tsx`'s filter chips, and `/nutrition`'s own (differently-shaped, icon-over-label `glass` card) water quick-add buttons were left as they were, since the ask was specifically about this screen's badges reading like its own Home/CTA buttons, not a global chip restyle.

**Nutrition today** (`NutritionTile`) is deliberately compact — full-width rather than square, with no separate "Nutrition today" label taking its own line (the tile carries an `aria-label` instead, since the label text still needs to exist for accessibility even once it's no longer visually printed): the header row folds the icon badge directly into the calories line itself (`{totals.calories} /{goal} kcal` right next to the badge) with the goal-relative progress bar directly underneath, then one row of three macro chips — protein, carbs, fat — each showing its own value/goal and its own `nutrientStatus`-colored mini progress bar, so a macro that's over its limit is visually distinct from one that's merely logged. It no longer shows a water pill in its header — that moved out into `WaterTile`'s own row below once water grew from "one glanceable number" into a genuinely interactive tile, and showing the same figure twice would've been pure redundancy. It still gets the same bottom-right ghost-icon treatment as `WaterTile` below (a large translucent `Apple` outline) for the same reason — a fresh install's all-zero state doesn't fill even this shorter tile — and getting that watermark to sit *behind* the real content (rather than painting over it, which plain CSS painting order would do for an absolutely-positioned element placed first in the DOM) needs each content wrapper marked `relative`: a positioned element with `z-index: auto` still paints after non-positioned siblings regardless of DOM order, so without that, the icon would render on top of the numbers instead of behind them.

**Water** (`WaterTile`, full-width, directly below Nutrition) is the one tile on this screen that breaks `HomeScreen`'s own stated rule of never calling a store action directly — its four quick-add buttons (`WATER_QUICK_ADD`, shared with `/nutrition`'s own Water card via `lib/gym/nutrition.ts` so the two never drift on what "quick add" means) call `logWater(ml)` straight from the tap, no sheet, no navigation, no confirmation — exactly the "no extra taps" the feature exists for. That's also why it's a plain `<div>` rather than a `<button>` like every other tile: a `<button>` can't legally contain another interactive element (the same HTML-content-model rule `ThemePicker`'s color-swatch `<input>` ran into earlier), so the quick-add buttons need a non-button ancestor. Tapping the tile still opens `/nutrition` like every other tile does, but only via its own header row (icon badge + `{total} / {goal}` + chevron, using the same `formatLiters` helper `/nutrition` uses) — that row is the one real `<button>` here, a sibling of the quick-add row rather than a wrapper around it. Below the header: a goal-relative progress bar (when a goal is set), then the quick-add row itself. Same fixed `sky-400` blue as the rest of the app's water UI, same ghost-icon-bottom-right treatment as every other tile, for the same reasons documented in the sections above and below.

**Best lift** (`BestLiftTile`) is now the lowest-emphasis tile on the screen — smaller icon, padding and type than it had as a full `0.9fr` row, trading that height to `WaterTile`. Still a single horizontal row rather than a stacked block — icon badge, then the label + exercise name (`line-clamp-2`, not `truncate`: a one-line clamp is what clipped real names once this tile only had a third of the row's width as one cell of the original square 2×2/3-column grid, and going full-width alone wasn't enough headroom for the longest names at a legible size, so the fix is letting the name wrap to a second line instead of shrinking the font further or accepting an ellipsis on a user's actual PR), then the `{e1rm} kg` pill on the right — same shape as the PR rows on `/history` (icon in a separate circle, not inside the pill; weight/reps as the usual subtitle is dropped here for space, since the pill number is the one figure this tile exists to show). Re-verified at the smaller scale against the same worst case as before — the catalog's actual longest exercise name, "Dumbbell Overhead Triceps Extension" at 35 characters — rather than assuming the original sizing story still held once both the row height and the tile's own type scale shrank.

Two navigation targets that used to point at `/` were repointed as part of the original move to add this screen: `session.tsx`'s "Build a workout" button (shown when `/session` is opened with no `activeWorkout`) now goes to `/generate`, since that CTA's whole point is landing directly in the generator, not a summary screen. `session.tsx`'s in-session "Close session" (✕) button and its cancel-workout confirmation, by contrast, deliberately still navigate to `/` (Home) — closing or cancelling a session is "step away from what you were doing," and Home is the app's neutral landing hub (its hero picks the session back up via "Resume" if it's still running).

`RootShell` (the `<html>`/`<head>`/`<body>` shell, separate from `RootComponent`) includes a small inline `<style>html,body{background-color:#000}html{color-scheme:dark}</style>` in `<head>`, ahead of the external `styles.css` `<link>`. The app's actual black background is entirely CSS-driven (`--background` in `styles.css`), which means on a cold/slow load there's a real window between the browser parsing the bare HTML and that external stylesheet finishing its network round-trip during which `<html>`/`<body>` have no background set at all — the browser's default white paints through in that gap (confirmed via a throttled-network Playwright test: `rgba(0,0,0,0)`, i.e. fully transparent, at the earliest sample without this rule). The inline rule applies the instant the HTML parses, no request to wait on, so there's nothing to flash before `SplashScreen` gets a chance to paint over it. This fixes the flash for a regular browser tab, but NOT for an installed iOS home-screen PWA (`apple-mobile-web-app-capable`) — there, iOS shows its own native launch screen before any of the page's HTML/CSS/JS runs at all, a separate mechanism no in-page fix can reach, and iOS's support for using the manifest's `background_color` (already correctly `#000000`) for that screen has long been inconsistent across versions. The reliable fix is the `head()` route config's `apple-touch-startup-image` link tags: one solid-black PNG per common iPhone screen size (`public/pwa/splash/*.png`, generated via a one-off Python/PIL script — device pixels = CSS points × that device's pixel ratio), each scoped to exactly that device via its `media` query (`device-width`/`device-height`/`-webkit-device-pixel-ratio`/`orientation: portrait`, portrait-only since the app doesn't support landscape), so iOS shows black immediately instead of defaulting to white while the page loads. Those media queries match on exact device dimensions, so this list is a real, ongoing gap rather than a one-time job — any device released after it was written (or just not covered) matches none of them and gets iOS's white default regardless of the fix being in place, which is exactly what reintroduced the flash for one such device. The `apple-touch-startup-image` entry with no `media` attribute at all closes that gap — Safari falls back to it whenever nothing more specific matches, reusing the largest existing splash PNG rather than shipping a dedicated asset, since exact pixel fit doesn't matter for a flat color.

That still wasn't the whole story: a report of the flash persisting even after a clean reinstall (which forces iOS to re-fetch the manifest/head) pinned the timing more precisely — solid black first (confirming the launch-image fix above **was** working), then a brief white flash, then the splash's own badge animation begins. That sequence sits in a third, distinct gap from the two above: after iOS's native launch image hands off to WebKit, but before WebKit's first actual paint of the page's own content (inline-style included) — and it traces back to `color-scheme` never being declared anywhere. WebKit uses `color-scheme` for more than form-control/scrollbar theming: absent it, its default is `light`, which is also the default canvas color it paints for that very first frame, before any author CSS — even a synchronous inline `<style>` — has had a style/layout pass run against it. Declaring `color-scheme: dark` (both as `<meta name="color-scheme" content="dark">` in `head()`'s `meta` array and, belt-and-suspenders, in the inline `<style>` itself, since that's guaranteed to apply with zero dependency on `HeadContent`'s own render order) tells WebKit its default canvas is dark too, closing that gap. `styles.css`'s `html` rule under `@layer base` also sets `color-scheme: dark` for consistency once the stylesheet itself has loaded.

A follow-up report — the flash still happening on almost every cold launch, but at inconsistent timing and intensity, and specifically NOT on a warm resume (switching back without force-quitting) — pointed at a fourth, still different gap, this time not fixable from CSS/meta at all: `public/sw.js`'s navigation handler was network-first, so a cold launch's very first HTML response (the one the launch image is handing off into) was always gated on a real network round-trip — DNS, TLS, Cloudflare's own cold start, whatever the radio's signal happened to be that moment — whose latency naturally varies launch to launch, tracking exactly the reported variability. Until that response starts arriving, nothing on the page (inline style, `color-scheme`, none of it) has reached WebKit yet. Switched to stale-while-revalidate instead: serve the cached shell immediately if one exists (near-zero latency, so there's almost nothing left for the launch image to hand off into), while still fetching a fresh copy in the background — handed to `event.waitUntil` rather than awaited, since once the cached response has already been returned the SW is otherwise free to terminate before that background fetch/`cache.put` finishes — to keep the cache current for the next launch. Safe to do here specifically because the app's markup doesn't embed per-request server data (everything hydrates from `localStorage` client-side), so a cached shell is functionally identical to a fresh one even across a deploy. Note this fix has a real, iOS-specific caveat the next one below doesn't share: a service worker evicted from memory during backgrounding has to wake back up before it can intercept anything, and on a true cold launch that wake-up racing the very first navigation request isn't guaranteed — so this fix may not always get the chance to run on the exact request that matters most.

A cold launch also fetches `manifest.webmanifest` and the `apple-touch-icon`/`apple-touch-startup-image` PNGs under `public/pwa/` themselves — separate network requests from the HTML document, un-intercepted by the service worker (which only ever handled `/tesseract/` and navigations) and, before this, served with no explicit caching at all beyond the default `/assets/*` rule that Nitro's pre-bundled Vite config auto-generates for the hashed JS/CSS bundle only. Every one of those is a plausible source of the same cold-launch-only, variable-timing flash: these are exactly the resources iOS needs before it can paint the native launch screen at all, so their fetch latency (again, real and launch-to-launch variable) is time the user sees whatever iOS defaults to first. `public/_headers` (a source file Nitro merges with, rather than overwrites with, its own auto-generated one — confirmed by inspecting `.output/public/_headers` after a build) adds `Cache-Control: public, max-age=31536000, immutable` for `/manifest.webmanifest` and `/pwa/*`. This is a real staleness tradeoff, the same one `/assets/*`'s own immutable caching accepts (justified there by content-hashed filenames; here by these being infrequently-changed, effectively-static assets instead) — a future change to any of these specific files won't reach an already-installed device until its cached copy expires or the app is reinstalled.

**The actual root cause, found last:** `styles.css` (~94KB) was linked as a plain render-blocking `rel="stylesheet"`, and a render-blocking stylesheet gates the **entire** first paint — the inline `<style>` above very much included. So none of the black-background work could paint until that file arrived, and it was the one thing in the critical path still reachable over the network: it lives under `/assets/*` (HTTP-immutable, but iOS evicts the HTTP cache aggressively for PWAs, and a reinstall guarantees an empty one) and `sw.js` never cached it either, since that only ever handled `/tesseract/` and navigations. The decisive clue was that the flash never appeared on a Safari reload: Safari holds the previous frame until the new page's first paint, so a delayed first paint is invisible there, while a cold PWA launch has no previous frame and shows the OS backdrop instead. Three changes close it: (1) `RootShell` loads `styles.css` non-blockingly — an inline script creates a `rel="preload" as="style"` link and flips it to `rel="stylesheet"` on load (injected from script rather than emitted as a tag plus an id-lookup swap, so it can't break on React's head hoisting; `error` and a 3s timeout also flip it, so a failed preload degrades to a normal blocking fetch rather than an unstyled app, and a `<noscript>` link covers JS-off); (2) the inline critical CSS grew to cover the whole first paint on its own — `#forge-boot` (SplashScreen's root, renamed at your peril) is painted fixed/inset-0/black there, which also hides the otherwise-unstyled `TabBar` buttons underneath, since UA-default buttons render light grey; and (3) `sw.js` now serves `/assets/*` cache-first (safe without revalidation because Vite content-hashes every filename, so a hit can never be stale) and precaches the shell during `install`, so even the first cold launch after a reinstall is warm. One non-obvious wrinkle: `color-scheme: dark` makes WebKit's *default* text color white, so with Tailwind not yet applied the FORGE wordmark and the `currentColor` SVG painted white-on-black — measured at ~2.4k bright pixels including pure white. Hence `html.css-pending #forge-boot *{visibility:hidden}`, with `css-pending` added by that same inline script and removed on all three of its paths (added from script, never baked into the SSR'd HTML, so a JS-off client can't end up permanently blank). Verified with a Playwright run that delays the stylesheet by 1.5s: mid-gap the viewport is 351,348/351,348 pure black pixels, zero bright; after it lands the badge is 96px and the wordmark `oklch(0.98 0 0)`; the abort path reveals unstyled-but-visible content; JS-off renders via `<noscript>`.

That introduced its own regression, reported as an unstyled "outline" of the badge/wordmark flashing before the real render: the success path flipped `rel` to `"stylesheet"` and removed `css-pending` in the *same synchronous tick*. Setting `rel` only **starts** the browser applying the new CSS (parse/recalc/layout) — it doesn't finish before the next line runs — so content could become visible via the default `visibility` before Tailwind's styles had actually painted against it. First attempt: defer the reveal to a double `requestAnimationFrame` after the flip. That checked out in this environment's only available browser engine for testing (a Chromium-only Playwright install, no WebKit build) — zero frames of visible-but-unstyled content across 84 sampled frames of a delayed load — but a real-device report said the outline still showed up on iOS Safari. The double-rAF was a timing assumption (that flipping to `rel="stylesheet"` reuses the already-fetched preload response near-instantly), and WebKit is documented as sometimes re-fetching rather than reusing the preload on exactly that swap, which would blow right past two frames' worth of margin.

Replaced the timing guess with an actual readiness check: poll `link.sheet.cssRules.length > 0` (wrapped in try/catch) via a capped `requestAnimationFrame` loop (120 tries, ~2s) before revealing — this confirms the CSSOM has genuinely been built from the stylesheet, correct regardless of how many times the browser (re)fetches internally to get there, rather than assuming a fixed number of frames is enough. `reveal()` also gained a `settled` guard so the two independent paths that can call it (the poll succeeding/capping vs. the outer 3s `setTimeout` backstop) can't double-fire. The error/timeout paths still reveal immediately — no valid CSS is arriving to paint against on those, so there's nothing to gain by waiting. Verified against a scenario Playwright's Chromium happened to reproduce naturally in dev mode (two real requests to `styles.css`, not a simulated one): sampling the badge's computed style every frame, zero violations across 105 samples — width resolves to the Tailwind-applied `96px` *before* `visibility` ever flips away from `hidden`, holding across both fetches. Re-ran the original pure-black check too (1.5s delay): still 0 bright pixels mid-load.

Still not it — a report that reproduced in plain Safari too (not just the installed PWA, ruling out every SW/caching theory in one step) described something more specific: the badge visibly rounding its corners over time, and the wordmark popping visible then fading back out, rather than either just snapping into place. Switching the readiness check again from `cssRules.length` to polling `getComputedStyle(html).getPropertyValue('--background')` (a plain custom property only `styles.css`'s `:root` sets, so its presence is unambiguous proof styles.css has actually been *applied*, not just fetched or parsed) reproduced the exact same thing, which was the tell that this was never a reveal-timing bug at all: `border-radius` was measured moving through intermediate values (0px → 3px → 4.87px → 7.06px → … → 32px) over real time, *while already revealed* — a value that should only ever be one of two states (unstyled `0` or `rounded-[2rem]`'s `32px`) was visibly interpolating between them.

Root cause: `duration-[500ms]` (the badge) and `duration-[550ms]` (the wordmark's own `transition-all`) compile to a flat `transition-duration` unconditionally — confirmed in the built CSS output (`.duration-\[500ms\]{--tw-duration:.5s;transition-duration:.5s}`) — regardless of whether a `transition` utility is present alongside them, and `transition-property` defaults to `all`. So these elements carry an active transition on every property from the moment they exist. The very first time their styles resolve — the jump from unstyled (`border-radius:0`, default opacity `1`) to Tailwind's real values (`rounded-[2rem]`'s `32px`, `opacity-0` while `textVisible` is still `false`) — gets caught by that transition and animates over hundreds of ms instead of applying instantly, exactly matching both reported symptoms. This bug was always latent in the original markup; it's invisible whenever styles.css blocks first paint (the *original* bug this whole mechanism exists to fix), since there's never an unstyled state to transition *from* in that case. Making CSS non-blocking is what first made an unstyled state observable at all, which is what surfaced this — no amount of retiming the reveal could have fixed it, since the transition itself was the bug, not when it became visible.

Fix: `no-transition` (a class alongside `css-pending`, same add-at-load/remove-at-reveal lifecycle, its own rule `html.no-transition #forge-boot *{transition:none!important}`) blocks all transitions under `#forge-boot` for that entire window, so the first unstyled-to-styled jump can only ever apply instantly. Legitimate transitions — the wordmark's own opacity fade, driven later by React's `textVisible` state — are unaffected, since by the time that fires, `no-transition` is long gone and the jump it exists to suppress already resolved. Verified by sampling `border-radius` on the badge and the wordmark container's actual opacity (not the `<p>` itself — opacity lives on its parent) every frame through the same natural two-fetch scenario: `border-radius` now jumps directly from `0px` to `32px` with zero intermediate values, at every sampled frame including before reveal; wordmark opacity holds at a clean `0` throughout, no pop-then-fade. Pure-black regression check still clean too.

A report that this was a real, large improvement but not a total fix narrowed things down to what was, at the time, thought to be what's left uncovered: the actual SSR'd HTML document response itself (the one `sw.js`'s stale-while-revalidate handling targets) had no `Cache-Control` of its own, and — per the SW fix's own caveat above — a cold launch's very first navigation isn't guaranteed to reach the service worker's fetch handler at all, if the SW was evicted from memory and hasn't woken back up in time to intercept it. Plain HTTP `Cache-Control`, by contrast, is checked by the browser's network stack itself, a layer that request reaches regardless of whether a service worker gets involved — making it the one remaining mechanism that still helps even when that race is lost. `src/server.ts` (the custom Cloudflare Worker entry `vite.config.ts`'s `tanstackStart.server.entry` points at, already wrapping the real TanStack Start handler for SSR error normalization) now also runs every response through `withDocumentCaching`: for a successful (`200`), `GET`, `text/html` response with no `Cache-Control` of its own already, it adds `public, max-age=3600`. Scoped tightly on purpose — method/status/content-type/existing-header checks all have to pass — so it only ever touches the actual document shell, never a server function response, an error page, or a POST. Safe for the same reason the SW and `/pwa/*` caching are: no route's HTML embeds per-request server data, so a browser serving a recent cached copy is indistinguishable from a fresh fetch. The `max-age` is deliberately much shorter than `/manifest.webmanifest`/`/pwa/*`'s year-long one, specifically because this is the layer meant to keep working even if the SW's own revalidation doesn't run — an hour bounds how stale the shell can get in that worst case, rather than leaving it to whenever the device happens to evict its cache.

All of the above optimizes a cold launch's *speed* by aggressively caching the shell at three layers (SW `PAGES_CACHE`, SW `ASSETS_CACHE`, and the document's own hour-long HTTP `Cache-Control`) — but every one of those caches is also a window during which a device can be holding an app shell from *before* a deploy while the deploy has since replaced the content-hashed JS/CSS files that shell's `<Scripts/>`/`<link>` tags point at. Reported in the wild: an installed PWA stuck showing only the splash's badge/bar (pure CSS, plays fine from the SSR'd markup with zero JS) with no "FORGE" wordmark (gated by React state that never arrives) and no way past it — not even force-quitting and reopening, since that just re-served the same stale cache again. Only deleting the Home Screen icon and reinstalling fixed it, by forcing a genuinely fresh fetch outside all three cache layers at once.

Two changes close this instead of relying on a user to know that trick. First, `RootShell`'s `<head>` gained a second inline script (self-contained, no dependency on the app's own JS bundle actually loading, since that's exactly what might be broken): a capture-phase `window` `error` listener catches a failed `<script>` tag (resource-load errors don't bubble, but capture-phase dispatch to ancestors still happens regardless), and an `unhandledrejection` listener catches a failed dynamic `import()` (the exact wording varies by engine, hence a loose regex match). Either one triggers up to two auto-reloads, spaced 1.2s apart to give the SW's already-in-flight background revalidation a real chance to land a fresh shell before the retry actually lands. If it's still failing after that — genuinely offline, say — a plain, Tailwind-independent fallback (`document.createElement` + inline `style` attributes, no CSS classes) renders a "Forge couldn't finish loading — Reload" button instead of looping forever, since Tailwind's own stylesheet may be exactly what failed to load too. The attempt count lives in `sessionStorage` (survives the reload it triggers) and is cleared by `RootComponent`'s own mount effect once hydration actually succeeds, so one bad launch's retry budget doesn't carry over and poison an unrelated later failure. Second, `sw.js`'s `CACHE_VERSION` was bumped — changing the file's own bytes is what makes a browser notice there's a new service worker to install at all, and `activate`'s existing cleanup (delete every cache key not in `CURRENT_CACHES`) then clears the stale entry out from under any device still running the previous version. `CACHE_VERSION` needs bumping by hand on any future deploy where this class of staleness could matter — there's no build-time automation for it, since `sw.js` is a hand-written static file outside Vite's pipeline (see its own header comment for why).

That covers a *broken* stale shell (one whose asset references 404), but not a merely *outdated-but-still-working* one — a deploy that changes visible UI (a moved tab, a redesigned card) without deleting any asset the old shell references leaves the old shell loading successfully, so nothing errors and the auto-reload script above never fires. Reported separately: force-quitting and reopening didn't pick up a UI change even though the deploy itself was healthy. Two gaps combine here: iOS Safari's own check for a new `sw.js` is lazy/throttled rather than running on every foreground, and even once a new SW *does* win the race (ours calls `skipWaiting()`/`clients.claim()` unconditionally, so it takes over automatically once installed), nothing told the already-open page that happened — the old JS/HTML already in memory just keeps running until something actually reloads it. `pwa.ts`'s `registerServiceWorker()` now calls `registration.update()` immediately after registering AND on every `visibilitychange` back to `"visible"` — this is the actual fix for "force-close and reopen doesn't update," since it turns that gesture into an explicit "check the server for a newer sw.js right now" rather than hoping the browser's own schedule happens to line up. Separately, `registerServiceWorker()` also tracks whether a controller was already active *before* this registration (`hadControllerAtLoad`) and, if a `controllerchange` fires afterward, dispatches a `forge:update-available` window event — guarded on `hadControllerAtLoad` specifically so a page's very first-ever SW activation (no previous controller, nothing to "update" from) doesn't misfire as an update. `UpdateBanner.tsx` (mounted once in `RootComponent`, alongside `SplashScreen`/`TabBar`) subscribes via `pwa.ts`'s exported `onUpdateAvailable()` and shows a small dismissible-by-reloading pill ("A new version is ready" + Reload). Deliberately a prompt, not an automatic `location.reload()` — the new shell is already active and will apply on the next navigation regardless of whether this banner ever appears, but yanking the screen out from under someone mid-workout or mid-typing would be worse than leaving them on the old shell a little longer.

`onUpdateAvailable`'s prompt still depends on `registration.update()` actually finding sw.js's own bytes changed — a deploy that only changes app UI, without touching `sw.js`, never trips it, since the stale content lives in Cache Storage regardless of whether sw.js itself changed, and that layer normally only self-corrects via the navigate handler's own background revalidation (which, per the caveat above, can silently lose the race against iOS evicting the service worker before it completes). `settings.tsx`'s "Force update" row (`### About`) is the deliberately blunter escape hatch for exactly that gap: `pwa.ts`'s `forceUpdate()` unregisters every service worker and deletes every Cache Storage key for the origin, then calls `location.reload()` in a `finally` (so it still reloads even if unregistering/clearing throws) — the in-app equivalent of deleting and reinstalling the Home Screen icon, but running from already-live JS instead of depending on a background fetch that might never get the chance to finish. A reload navigation revalidates with the server rather than trusting a cached response outright, so it also gets past the document's own hour-long HTTP `Cache-Control` once the SW/Cache Storage layers are gone. The button shows a spinning `RefreshCw` + "Updating…" while this runs and is never expected to resolve normally — the page navigates away before its `async` body would otherwise return, so there's nothing to reset it back to non-updating state, deliberately.

### App state: one localStorage-backed context

Nearly all app state (equipment profiles, workout history, the in-progress `activeWorkout`, unit/accent/sound settings) lives in a single React Context defined in `src/lib/gym/store.tsx` (`GymProvider` / `useGym()`), persisted whole to `localStorage` under `forge.gym.state.v2` (with a `migrate()` step for older saves). There's no reducer/redux — `useGym()` exposes direct action functions (`startWorkout`, `logSet`, `finishWorkout`, `cancelWorkout`, `swapActiveExercise`, etc.) that each call `setState` internally. New cross-screen state should go here rather than component-local state or a new context.

### Exercise catalog: seed data mutated in place

`src/lib/gym/data.ts` exports a mutable `EXERCISES` array (the seed/fallback list). `src/lib/gym/catalog.ts` fetches the live catalog from Supabase and calls `EXERCISES.splice(0, EXERCISES.length, ...list)` to patch it **in place**, then bumps a version counter that `useExerciseCatalog()` (a `useSyncExternalStore` hook) uses to re-render subscribers. This means `EXERCISES` is imported directly (not through the hook) in several places (`generator.ts`, `session.tsx`) and relies on the splice-in-place mutation to see updates — don't reassign `EXERCISES` to a new array anywhere, and prefer `useExerciseCatalog()` in components that need to re-render when it changes. `refreshCatalog()` also caches the result to `localStorage` (`forge.exercise-catalog.v1`) and is kicked off once from the root route.

### Supabase

`src/integrations/supabase/*` is generated Supabase codegen; `client.ts` and `types.ts` are headed "This file is automatically generated. Do not edit it directly." Supabase serves two roles: the exercise catalog (CRUD in `exercises.tsx` / `catalog.ts`, world-readable/writable — no auth required) and, since the cloud-sync feature, optional per-user auth + backup of the whole `GymState` blob (table `user_gym_state`, one row per `auth.uid()`, RLS-restricted to its owner). `lib/gym/auth.ts` wraps `supabase.auth` (sign up/in/out, session listener) and the pull/push helpers; `GymProvider` (`lib/gym/store.tsx`) owns the actual sync — on sign-in it pulls the cloud row if one exists (cloud wins, for restoring on a new device) or pushes the current local state up as the first cloud copy, then keeps pushing local edits up on a debounce while signed in. The app remains fully usable signed-out — everything still round-trips through `localStorage` as before, cloud sync is additive, not a replacement.

### Nutrition label scanning (Gemini, server function)

`src/lib/gym/labelScan.ts` defines `scanNutritionLabel`, the app's first TanStack Start server function (`createServerFn`) — it runs server-side only, so the `GEMINI_API_KEY` env var it reads (`process.env["GEMINI_API_KEY"]`, no `VITE_` prefix — never sent to the client) never reaches the browser. `AddFoodSheet.tsx`'s "Scan nutrition label" flow calls this function, which sends the photo to the free-tier `gemini-3.5-flash-lite` model with a JSON response schema (calories/protein/carbs/fat/fiber/salt, normalized to per-100g, plus a best-effort product name) and returns the parsed result to pre-fill the same editable per-100g form manual entry uses. If `GEMINI_API_KEY` is unset or the request fails, the sheet falls back to its existing manual-entry path rather than crashing — cloud-dependent features in this app degrade gracefully, matching the Supabase pattern above. Before upload, `fileToBase64` downscales the photo client-side (`createImageBitmap` → canvas, capped at 1280px on the long edge, re-encoded as JPEG q0.85, `imageOrientation: "from-image"` to respect EXIF rotation) rather than sending the camera's full-resolution original — a label's print stays perfectly legible well below that, and a smaller image means less to upload and fewer tiles for Gemini to process, so this is most of the scan's latency. Falls back to the original file untouched if resizing throws for any reason (a slower scan beats a broken one).

### Barcode scanning

A second, independent scan path alongside the label scan above, for packaged foods already in a product database — `AddFoodSheet.tsx`'s "Scan barcode" button opens `components/gym/BarcodeScanner.tsx`, a full-screen `fixed inset-0 z-[60]` camera overlay (a layer above the sheet's own `z-50`, not another step inside it, since it needs the whole viewport for the live preview rather than the sheet's bounded height). It decodes continuously against the camera stream via zxing-js (`BrowserMultiFormatReader.decodeFromVideoDevice`, which also requests the camera and prefers the back/environment-facing one) rather than the browser's native `BarcodeDetector` API, which iOS Safari — this app's primary target — doesn't reliably support. `@zxing/browser` (~200KB gzipped) is dynamically `import()`-ed inside the scanning effect rather than at module scope, so it's fetched only the first time someone actually opens the scanner, not as part of every nutrition-page load (confirmed in the built output: the main client bundle has zero references to it, and it lands in its own chunk pulled in only from `BarcodeScanner`). On a decoded barcode, `lib/gym/barcodeLookup.ts`'s `lookupBarcode` looks it up against [Open Food Facts](https://world.openfoodfacts.org) — free, no-auth, CORS-friendly, so unlike `scanNutritionLabel` this runs as a plain client-side `fetch`, no server function or API key involved — and returns the exact same shape `scanNutritionLabel` does (reusing its `ScannedLabel` type), so `AddFoodSheet`'s `applyScanResult` helper fills the review form identically from either path. A barcode simply not being in the database is a normal outcome, not an error: `lookupBarcode` returns `null` for it (distinct from a thrown network/request error), and `AddFoodSheet` shows a dedicated "couldn't find that product" message pointing at the label-scan or manual-entry fallbacks rather than a generic failure. The scanner's `useEffect` also handles the fast-tap race where the overlay closes before `decodeFromVideoDevice`'s promise resolves — the camera stream is stopped the instant it arrives instead of leaking — and keeps `onDetected`/`onClose` in refs so the effect only restarts when the scanner itself opens or closes, not on every parent re-render.

### Bottom sheets save on Done, not just their explicit save button

Every `BottomSheet` gets a header "Done" button for free (`BottomSheet.tsx`), wired to whatever `onClose` the caller passes — and a fair number of sheets build a draft in local state that's only meant to be committed once, via their own `close()` wrapper around that `onClose`. The rule those wrappers follow: if the draft is fillable/save-worthy at all, Done (and the backdrop tap, which calls the same `onClose`) commits it exactly like the sheet's own primary button would, rather than silently discarding whatever's already been filled in — a user who scans a label, fills in a meal's ingredients, or types in nutrition limits and then taps "Done" instead of hunting for a separate save button shouldn't lose that work. `AddFoodSheet.tsx`'s `close()` calls the same `persistEdits()` its "Add to log" button calls whenever `step === "review"` (covering a fresh scan/manual entry and an edit alike, not just editing as it originally did); `CreateMealSheet.tsx`/`CreateRecipeSheet.tsx` mirror this with their own `persist()` helper shared between `close()` and `save()`; `NutritionGoalsSheet.tsx` does the same for its numeric-limits draft. The explicit button (`"Add to log"`, `"Save meal"`, etc.) still renders alongside this for a fresh entry — it's the expected primary action — except where a sheet already established a save-on-close-only convention (an existing `editEntry`, where a redundant second button would just be visual noise). This intentionally does NOT extend to multi-step *setup wizards* (`WeeklyPlanSheet`, `ProgramBuilderSheet`'s `template`/`days`/`weeks` flow) — there, backing out via Done mid-wizard is a legitimate "I changed my mind," not an accidental loss of a finished entry, so those keep the plain discard-on-close default.

### Nutrition history and meal templates

The Nutrition screen isn't today-only: `dayOffset` state (0 = today, negative = back) drives `entriesForDay`/`dailyTotals` over whichever day is selected, and "Add food"/"Meals" are hidden on non-today days (editing/deleting a past entry is still allowed). `MealTemplate` (`lib/gym/nutrition.ts`) is a named, saved combo of `MealIngredient`s (each just `{name, grams, per100}`) — `store.tsx` holds them in `mealTemplates` and exposes `saveMealTemplate`/`deleteMealTemplate`/`logMealTemplate` (the last one writes one `FoodEntry` per ingredient in a single `setState`, all sharing one `logged_at`/`meal`). `CreateMealSheet.tsx` builds one by reusing `AddFoodSheet` itself for each ingredient — pass it an `onIngredientCaptured` callback and it captures `{name, grams, per100}` to that instead of writing to the food log (hiding the now-irrelevant meal-type picker). The two sheets are never both mounted-open at once (`CreateMealSheet`'s own `<BottomSheet open>` is `false` while `AddFoodSheet` is up) specifically to avoid stacking two `fixed inset-0 z-50` overlays.

### Saved recipes

`Recipe` (`lib/gym/nutrition.ts`) is deliberately a different concept from the `MealTemplate` above it, not a rename of it: a `MealTemplate` logs every ingredient as its own `FoodEntry`, unscaled, every time — it's "this exact combo, again." A `Recipe` adds `servings` (how many the whole batch yields) and is meant for a home-cooked batch eaten across several sittings: `recipePerServing()` divides the ingredients' combined `dailyTotals()` by `servings` to get one serving's macros, and `store.tsx`'s `logRecipe(id, servings, meal)` writes a *single* `FoodEntry` for however many servings were actually eaten — named after the recipe, not one row per ingredient — rather than the whole-batch entries `logMealTemplate` writes. That entry reuses the existing `grams`/`per100` scaling machinery (`scaledMacros`) purely as an encoding trick: `grams` is set to `servings * 100` and `per100` to the recipe's per-serving macros, so `N` servings scale out to exactly `N ×` per-serving macros through the same math every other food entry already goes through — there's no parallel "servings-based" entry shape to keep in sync elsewhere in the app (history, daily totals, the Home dashboard's nutrition tile all keep working unmodified). `CreateRecipeSheet.tsx` mirrors `CreateMealSheet.tsx` almost exactly (same ingredient-building-via-`AddFoodSheet` pattern) plus a servings stepper; the Recipes list on `/nutrition` shows each recipe's per-serving calories and a one-tap "log 1 serving" button — logging more than one serving at once isn't a separate flow, it's just editing that logged entry's `grams` afterward (200 = 2 servings, since `per100` already means "per serving").

### Water tracking

`WaterEntry` (`lib/gym/nutrition.ts`, `{id, ml, logged_at}`) is deliberately its own minimal shape rather than bolted onto `FoodEntry` or `NutritionGoals` — water isn't a macro, so forcing it through either would mean fields that don't apply everywhere else those types are used. `store.tsx` holds `waterEntries` and an optional `waterGoalMl`, with `logWater(ml)`/`removeWaterEntry(id)` actions; the goal itself has no dedicated setter and is just written through the store's existing generic `update({ waterGoalMl })`, the same way `supersetsEnabled` and `nutritionProfile` are — a single optional scalar doesn't need its own action. `entriesForDay` (previously typed to `FoodEntry[]` only) is now generic over any `{ logged_at: string }[]`, so the Nutrition screen's existing `dayOffset` day-picker applies to water the same way it already does to food, with no parallel filtering logic. The Water card sits directly under the calories/macros overview: a running total, a goal-relative progress bar, four quick-add buttons (250ml/500ml/750ml/1L), and — only on today, mirroring "Add food"/"Meals" — a horizontally-scrolling strip of removable chips, one per logged entry. Water's progress bar and quick-add icons originally used a fixed `sky-400` blue everywhere, on the same "content-intrinsic color" reasoning `SplashScreen`'s sparks and `Confetti`'s palette already establish — but that read as clashing chrome once `WaterTile` made water a prominent, always-visible Home tile rather than an occasional pill, especially against a non-blue accent. Reverted to following the accent almost everywhere: the progress bar (both `/nutrition`'s Water card and `WaterTile`) follows the accent, and every quick-add button/icon (both places) is accent-colored rather than fixed blue — though the two no longer share one literal class string, see "Icon badges are solid-fill, not tinted" below for why `WaterTile`'s own quick-add pills in particular moved to `bg-primary`/`text-primary-foreground`. The one deliberate holdout is `WaterTile`'s own header badge icon (the small circled `Droplet` next to the total, on Home only) — still fixed `sky-400`, so water keeps exactly one reliable "this is water" visual anchor at a glance across any accent, the same job the old blanket rule used to do for the whole feature. Nowhere else — not the ghost watermark, not `/nutrition`'s Water card (which has no equivalent badge icon to begin with) — keeps the fixed blue.

**Home dashboard integration**: Recipes still gets no Home presence at all, per the same reasoning that already dropped Saved Templates and Last Session from `index.tsx` — it's one tap away via `/nutrition`, exactly like Saved Templates is one tap away via `/generate`. Water's own Home integration went the opposite direction from that minimal-by-default rule, though, and deliberately so: it started as a small pill folded into `NutritionTile`'s header (zero extra vertical cost, invisible until `waterMl > 0`), but grew into its own full `WaterTile` row with working quick-add buttons once the ask became "let me log water from Home without extra taps," which a static pill fundamentally can't do — see "The stat grid"/"Water" above for the tile itself, and `WaterTile`'s own comment in `index.tsx` for why it's the one tile that breaks `HomeScreen`'s read-mostly rule. Promoting it to a full row is also *why* the grid went from three rows to four and every other tile's share got re-derived — this wasn't a free insertion, it came out of Best lift's height specifically (see "The stat grid" above).

### Profile avatars

`src/lib/gym/avatars.ts` defines a fixed list of 6 `AvatarOption`s (id, label, a `lucide-react` icon, and an `oklch()` circle background — same color formula `ThemePicker.tsx` uses for accent swatches). The chosen `avatarId` lives on `GymState` (default `"bot"`, migrated with `raw.avatarId ?? DEFAULT_AVATAR_ID`) and is set via the store's generic `update({ avatarId })` — there's no dedicated action. `AvatarPicker.tsx` (in Settings, between Account and Appearance) renders the selectable grid **using each option's own fixed `bg`** — deliberately distinct per avatar there, so the 6 choices read as different colors to pick between. `ProfileAvatar.tsx` renders the chosen one anywhere it needs to be displayed (currently just the profile/settings button in the `index` route's header) but does NOT use `avatar.bg` — it's `bg-primary`/`text-primary-foreground`, so the one place the avatar is actually shown in the app follows whichever accent the user picked, rather than being stuck at its per-character preset color regardless of theme.

The `index.tsx` header button wrapping `ProfileAvatar` needs `flex items-center justify-center` itself (not just on the avatar span it contains) — Tailwind v4's preflight doesn't zero out native `<button>` padding the way v3's did, so an unstyled/asymmetric UA default button padding was pushing the 40px avatar off-center within the button's own box despite the avatar span being internally centered. That fixed the avatar's centering within its own button, but not the button's position within the header bar as a whole — a follow-up report showed it sitting near the top of the bar rather than centered against the full title+subtitle block. That's `Screen.tsx`'s own header grid (`grid-cols-[minmax(0,1fr)_auto] items-center gap-3`, previously `items-end`): `items-end` was bottom/baseline-aligning the `action` slot against the title+subtitle column instead of centering it against the full row height, which reads as "stuck near the top" whenever the title block (two lines, with a subtitle) is taller than the action itself. `items-center` fixes both routes that pass an `action` (`index`'s profile button, `history.$workoutId`'s back chevron) — verified the profile button's vertical center now exactly matches the header row's own center (0px offset).

`ThemePicker.tsx`'s custom-color swatch (the conic-gradient wheel, `accent: "custom"`) has its `<input type="color">` as a **sibling** of the decorative swatch div, not nested inside a `<button>` — nesting interactive content inside a `<button>` is invalid per the HTML content model, and was silently breaking the native color picker on iOS Safari (tapping it did nothing). The input itself is the real interactive element now, absolutely positioned over the swatch and invisible (`opacity-0`) but still hit-testable; the swatch div underneath is purely decorative (`aria-hidden`).

### Rest-timer push notifications

`navigator.vibrate` (the `haptic()` helper in `store.tsx`) is a no-op on iOS — WebKit has never implemented the Vibration API there, on any browser, and there's no workaround. Separately, the in-app rest-complete `Notification` fired from `session.tsx`'s `onCountdownEnd` only works while the tab's JS is still running; iOS suspends a locked/backgrounded tab, so it can't fire once the screen is off. `lib/gym/push.ts` adds a real Web Push path for that case: `ensurePushSubscription()` (called from `toggleNotify` once permission is granted) subscribes via the service worker's `PushManager` and upserts `{device_id, endpoint, p256dh, auth}` to the world-writable (no-auth, like `exercises`) Supabase table `push_subscriptions` — `device_id` is a random UUID generated once and kept in `localStorage`, standing in for a proper user id. `startRest()` in `session.tsx` (wrapping `rest.start`) calls `scheduleRestNotification(seconds)`, which upserts a `fire_at` row into `rest_timer_notifications`; `onCountdownEnd` cancels it. A Supabase edge function (`supabase/functions/send-rest-notifications`), invoked every 6s by a `pg_cron` job (set up in the `add_push_notifications` migration), finds due rows, sends the push via `web-push` using a VAPID keypair, and clears the row (deleting the subscription too on a 404/410). `public/sw.js`'s `push`/`notificationclick` listeners display it. All of this degrades silently (wrapped in try/catch, never throws into the UI) if push isn't available — e.g. iOS only supports Web Push for a PWA added to the Home Screen, on iOS 16.4+. **Deploying this requires manual one-time setup outside the app's own CI** (no Supabase CLI credentials are available to this environment): apply the migration, `supabase functions deploy send-rest-notifications`, and set the function's `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` secrets — `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` are auto-injected into every edge function by Supabase and can't (and don't need to) be set manually; `secrets set` rejects any name starting with `SUPABASE_`. Also store the service role key in Supabase Vault (`SELECT vault.create_secret('<key>', 'service_role_key');` — see the migration file's comments) so the cron job's `Authorization` header can read it; a plain `ALTER DATABASE ... SET` for this doesn't work since the SQL editor's role isn't a superuser. The VAPID keypair itself isn't committed anywhere — it was generated once and handed to the project owner directly.

### Suggested nutrition limits

`lib/gym/nutrition.ts` exports `suggestNutritionGoals(profile: NutritionProfile)`, a pure calculator (no store/network access) that turns a short biometric profile into a `NutritionGoals` — Mifflin-St Jeor for BMR, `ACTIVITY_LEVELS`' factor for TDEE, a goal/pace-dependent adjustment for the calorie target (asymmetric: bulk surpluses are smaller than cut deficits at the same "aggressive" label, since a fast bulk mostly adds fat), goal-dependent protein g/kg, fat as ~28% of calories, carbs as the remainder, and fiber/salt from flat dietary-guideline constants. `NutritionQuestionnaireSheet.tsx` is a 4-step wizard (basics → activity → goal/pace → review) built on top of it; its "Use these limits" step both calls `update({ nutritionProfile })` (the raw answers, stored so reopening the questionnaire prefills instead of starting blank — has no effect by itself) and an `onApply(goals)` callback the caller decides what to do with. `NutritionGoalsSheet.tsx` is the only caller: `onApply` pre-fills its existing editable number-field draft (not a direct `setNutritionGoals` write), so a suggestion is a starting point the user can still hand-tune before saving, exactly like typing values in directly. The two sheets are never both open at once (same `open={open && !questionnaireOpen}` pattern as `CreateMealSheet`/`AddFoodSheet`) to avoid stacking two `fixed inset-0 z-50` overlays. Everything here is client-side math — no Supabase table or edge function involved.

### Loading indicator

`components/gym/DumbbellLoader.tsx` is the app's loading indicator — the app icon's own Dumbbell glyph (lucide's exact path data, tilted on its native diagonal — same as the tab bar's `Dumbbell` icon and the app icon itself, a flat lucide glyph, not a 3D render), its two weight-plate clusters sliding off along that diagonal while fading out, then back, looping. Used instead of a generic spinner (`AddFoodSheet.tsx`'s label-scanning step) and, on `index.tsx`'s "Generate workout" button, as an artificial ~1.5s "thinking" delay purely for feel — `generateWorkout()` itself is synchronous/instant, but firing it immediately made the button feel like it wasn't actually doing anything; `generate()` now sets `generating`, shows the loader + "Building your session…" in the button (disabled meanwhile) for 1.5s via `setTimeout`, then calls the real `build()`. Only that button gets this — `shuffle` (regenerating an already-visible plan) stays immediate. It's plain `currentColor` SVG shapes (no color baked in — takes it from `className` or just inherits, like any lucide icon) animated by the `dumbbell-plates` keyframes in `styles.css` (the `animate-dumbbell-plates` utility, driven by a `--dumbbell-slide-x`/`-y` CSS custom property each plate group sets to its own signed travel distance) — the opacity fade is timed to complete alongside the slide so a plate dissolves away before it'd visibly clip against the square viewBox, rather than sliding through a hard edge. Not a static image, so it matches "never hardcode colors in components" and follows whichever accent the user picked.

### Splash screen

`components/gym/SplashScreen.tsx` is mounted once in `__root.tsx`'s `RootComponent` (inside `GymProvider`, alongside `<Outlet />`/`<TabBar />`) — a `fixed inset-0 z-[100]` overlay on `bg-background`, choreographed as three clearly separated beats rather than everything animating in at once or overlapping into a blur: the glowing badge (an empty rounded square) scales/fades in completely alone first (`BADGE_MS`, 500ms, no delay); only once that's finished does the bar fade in and the barbell "fly in" — the two weight-plate clusters snap onto the bar and strike with sparks (`CLUSTER1_DELAY_MS`/`CLUSTER2_DELAY_MS`, both derived from `BADGE_MS` so the second beat can't start before the first one visibly finishes); only once that's settled does the "FORGE" wordmark fade in as the third beat. Every `animate-in` element here (the badge, the bar's `<path>`) carries an explicit `fill-mode-both` — `tw-animate-css`'s `animate-in` defaults to `animation-fill-mode: none`, and since this splash paints from SSR'd markup, without `both` telling the browser to hold the "from" keyframe (opacity 0, scaled down) until the animation actually starts, the element instead renders at its normal resting state (fully opaque, full size) for the instant between the stylesheet applying and the animation engine kicking in, then snaps back to invisible to actually begin — a real, reported flash landing right as the entrance animation starts (missed initially on the badge since the bar's `<path>` already had `fill-mode-both`, making it easy to assume the badge did too). The two weight-plate clusters aren't at risk of the same gap: their `dumbbell-flight`/`dumbbell-recoil` keyframes set `both`/`forwards` directly in the animation shorthand in `styles.css` rather than relying on a separate utility class. A couple of the delay/duration pairs that tie these beats together have to be plain literal Tailwind arbitrary-value classes (e.g. `duration-[500ms]`) rather than interpolated from the `BADGE_MS`/`TEXT_TRANSITION_MS` constants — Tailwind's build-time class scanner can't see through a template-literal-interpolated arbitrary value and would silently emit no CSS for one — so those specific literals are commented as needing to stay in sync with the constant by hand; the one delay that structurally MUST stay exactly tied to `BADGE_MS` (the bar's fade-in delay) is set via inline `style` instead, which has no such scanning limitation. The two weight-plate clusters snap onto the bar via a one-shot, staggered reveal in `styles.css`; deliberately a bespoke inline SVG here rather than reusing the looping `DumbbellLoader`, since that component's animation always loops and this reveal needs to play once and hold.

Each cluster's landing is two chained CSS animations, not one, because "the moment of impact" and "the whole landing flourish" turned out not to be the same instant — a single overshoot-and-settle animation reaches the true contact point around a third of the way through, then overshoots past it and eases back, so anything synced to its declared *end* fires well after the metal actually touches the bar (read as sparks arriving for a delayed "celebration" beat, not as part of the impact). `dumbbell-flight` is the real travel — its 100% keyframe IS the contact point, full stop. `dumbbell-recoil` is a small, purely cosmetic post-impact bounce chained right after via a `--dumbbell-cluster-delay` custom property (both animations share it, staggering the whole two-stage motion per cluster) plus flight's own duration baked into recoil's delay; recoil uses `fill: forwards` rather than `both` specifically so it doesn't assert its resting transform during flight's own active phase and mask the travel.

Each `SparkBurst` (defined in `SplashScreen.tsx`) fires on a CSS `animation-delay` set to exactly `clusterDelay + FLIGHT_MS` (a named JS constant mirroring `dumbbell-flight`'s CSS duration) — a plain delay rather than firing off `dumbbell-flight`'s own `animationend` event, because this splash paints from SSR'd markup: the CSS animation can (and, reproduced empirically, regularly does) finish playing before React finishes hydrating and attaching that listener, silently dropping the event for whichever cluster lands first. A frozen-timeline event trace confirmed the fix: `spark-flash` now starts within a fraction of a millisecond of `dumbbell-flight`'s `animationend`, for both clusters, every time. `SparkBurst` fires a forceful 8-spark burst of `<line>`s radiating outward along a wide (~145°) cone of angles pointing away from the icon's center, each with its own reach/length/width varied by a fixed per-index formula (not `Math.random()`, which would mismatch between SSR and hydration) so the burst reads as an organic scatter rather than a uniform starburst — animated via `spark-fly`/`animate-spark` in `styles.css` (an overshoot-then-settle scale for a sharp launch, sparks reaching well beyond the badge itself, which needs `overflow-visible` on the `<svg>` for that to render uncropped), popping to near-full brightness within ~15ms of firing (3%/4% keyframe marks) rather than easing in over several tens of ms. Layered under the streaks, a bright white-hot `spark-flash`/`animate-spark-flash` circle and an expanding `spark-ring`/`animate-spark-ring` shockwave sell the impact instant itself — an anvil-strike flourish on the app's name. Sparks use a fixed warm "hot metal" palette (`SPARK_COLORS`, orange/gold/white-hot oklch tones, with the flash/ring using the brightest as `FLASH_COLOR`) rather than the user's accent color, same reasoning as `Confetti.tsx`'s own fixed palette: a forge spark reads as orange regardless of theme, since it's a content-intrinsic color rather than a themable UI element. `TEXT_DELAY_MS` (computed from the same `CLUSTER2_DELAY_MS + FLIGHT_MS + SPARK_FLIGHT_MS` constants, no separate magic number) waits for the second, later-firing burst to finish flying before the "FORGE" wordmark + tagline fade/slide in, so the name reads as forged by the strike rather than the sparks feeling tacked onto an already-revealed logo. Stays up until `hydrated` (from `useGym()`) is true AND at least `MIN_VISIBLE_MS` has passed since mount, then fades out over `EXIT_MS` (400ms) and unmounts itself for good. `MIN_VISIBLE_MS` is derived (`TEXT_DELAY_MS + TEXT_TRANSITION_MS + HOLD_MS`, ~2150ms total, ~2.5s including the exit fade — matching the target "around 2 to 2.5 seconds" for the complete splash) rather than a separately hand-tuned number, specifically so it can't quietly drift out of sync with the actual choreography the way it did earlier in this feature's history. Mounted once at the route root with local state that only ever moves forward, so client-side tab navigation never re-triggers it — strictly a cold-open, once-per-app-load thing.

### Workout generation & domain logic

- `lib/gym/generator.ts` — the core generation engine: picks a `Shape` (set/rest/rep scheme) based on requested duration, then fills it from `availableExercises()` (filtered by equipment) with compound-first, accessory-second logic; also estimates session duration.
- `lib/gym/anatomy.ts` — the `REGIONS` used by the muscle-map selector (front/back body regions), `PAIRINGS` (personal-trainer-style pairing suggestions like "pair Chest with Triceps"), and mapping from regions down to fine-grained `TargetMuscle`s.
- `lib/gym/antagonist.ts`, `lib/gym/plates.ts` — antagonist-pair detection (for superset labeling) and plate-math for the in-session plate-loading hints.
- `lib/gym/types.ts` — the shared domain types (`Exercise`, `Workout`, `PlannedExercise`, `LoggedSet`, `EquipmentProfile`, etc.) that basically everything above is built on.

### Progressive overload: double progression + plate-aware rounding

`lib/gym/progression.ts`'s `suggestWeight(exerciseId, workouts, targetReps, readinessScore?, roundStep?)` is a pure, stateless function recomputed on demand (never persisted) from the single most recent workout containing working sets for that exercise — it's a suggestion, not a stored plan. It implements **double progression**: `repRange()` parses a `target_reps` string like `"8-12"` into `[bottom, top]`; if every working set logged last time reached `top`, it suggests a ~2.5% weight bump (floored at one full `roundStep`) and resets the rep target back down to `bottom`; otherwise it suggests repeating the same weight and aiming for one more rep than the worst set last time (capped at `top`). `ProgressionSuggestion` carries both `weight` and `reps` together as one suggestion, plus `direction`/`bumped` (which icon to show) and a human-readable `reason`. When a readiness check-in exists for today, `readinessWeightFactor`/`readinessNote` (from `lib/gym/readiness.ts`) further scale the weight and append a note — a rough day trims it, a great one nudges it up — so the check-in actually changes what's suggested, not just logged.

`roundStep` (default `0.5` for callers without an `Exercise`/`EquipmentProfile` in scope) rounds the suggestion to a realistically loadable increment via `lib/gym/plates.ts`'s `plateStep(exercise, profile)` — the smallest jump actually achievable given the exercise's equipment and the user's owned plates/dumbbells (2× smallest owned plate for barbell/smith, a flat 2kg dumbbell-rack jump, 2.5kg otherwise). All three call sites that had `suggestWeight` before this round of work now pass a real `plateStep` instead of the 0.5kg default: `generator.ts`'s `makeEntry` (generation-time, via a new `profile?: EquipmentProfile` param on `GenerateArgs`), `index.tsx`'s `SwapSheet.onPick` (recomputed on exercise swap, `suggested_reps` dropped and regenerated alongside `suggested_weight` rather than left stale), and `session.tsx`'s live per-exercise badge (`step` now computed once per `ExerciseBlock` and threaded into both the suggestion and the +/- steppers, so the suggestion always rounds to the same increment the UI lets you actually dial in). The suggestion badge in both the generated-plan card (`index.tsx`) and the live session (`session.tsx`) now shows `{weight}kg × {reps}`, not just the weight — the rep target is as much a live part of a double-progression suggestion as the weight is.

`session.tsx`'s `endWorkout()` now shows a post-workout **"Workout complete" summary** before navigating to History: it snapshots `plan` just before calling `finishWorkout()`, then — once the finish has committed (`workouts[0]` is the session that just ended) — renders one card per unique exercise in that plan with its fresh next-time `suggestWeight` prediction (no readiness score passed here, since "next time" is an unknown future day), each rounded with that exercise's own `plateStep`. This is the first thing progressive overload actually *shows* you after finishing, rather than only surfacing again the next time you happen to start that exercise.

### Program builder: bounded, multi-week wave periodization on top of the weekly split

`lib/gym/programs.ts` defines `Program` — a bounded sequence of `ProgramWeek`s (`{type: "build" | "deload", intensity: number}`) laid over a `ScheduleSlot[]` (the same `SplitTemplateId` + `dow`-per-day shape `WeeklyScheme` already used, from `lib/gym/splits.ts`), plus a `currentWeek`/`cyclePosition` cursor. `PROGRAM_PRESETS` ships three fixed waves (`wave_3`/`wave_4`/`wave_6`, 3/4/6 weeks) — each a short run of `"build"` weeks at slowly climbing intensity (1.0 → ~1.16) followed by one `"deload"` week at `0.6`. This is deliberately **not** a percentage-of-training-max system (Wendler 5/3/1-style): the app has no training-max concept, and inventing one just for this would be new, disconnected state rather than building on data the app already tracks. Instead, `intensity` is a plain multiplier applied on top of the existing history-based `suggestWeight()` suggestion at generation time — `generator.ts`'s `makeEntry` takes an optional `intensityMultiplier` on `GenerateArgs` and, when it's not `1`, rounds `suggestion.weight * intensityMultiplier` to the same `plateStep` the base suggestion used. A build week with no suggestion yet (no history for that exercise) generates exactly as it would without a program — there's nothing to scale.

`Program` and `WeeklyScheme` are independent, coexisting `GymState` fields — starting a program doesn't delete or migrate an existing weekly split. Where the index route's "This week" card would show one or the other, `program` wins when both exist (checked first in the conditional); the `weeklyScheme` branch gains a "Build a program instead" button as a soft upgrade path, and a fresh install with neither offers both ("Weekly plan" / "Program") side by side. `ProgramBuilderSheet.tsx` is a four-mode `BottomSheet` (`manage` shown whenever a program exists; `template` → `days` → `weeks` to build a new one) — `days` defaults to an even weekday spread per the template's `suggestedDaysPerWeek` (a small `EVEN_SPREAD` table deliberately duplicated from `WeeklyPlanSheet.tsx` rather than shared, keeping the two sheets independent) and lets any slot's day-of-week be edited later from `manage` mode via `updateProgramSlotDow`. Starting a program always resets `currentWeek`/`cyclePosition` to `0` (unlike `WeeklyScheme`, which picks the closest upcoming day via `initialCyclePosition`) — a program's week 1 day 1 is a deliberate, explicit start, not "whichever slot is soonest."

Advancing the program follows the same mutually-exclusive-by-construction flag pattern `WeeklyScheme` already established: `Workout.fromProgramDay` (parallel to the existing `fromScheduledDay`) is set only when a session is started via the program card's "Start {day} day" button (`index.tsx`'s `startProgramDay`/`start()`), and only such a session advances the cursor — an ad-hoc or repeated session doesn't silently skip the "real" next day. `store.tsx`'s `finishWorkout` calls `programs.ts`'s `advanceProgram()` when `activeWorkout.fromProgramDay` is true: it increments `cyclePosition`, and once that reaches the end of `schedule`, it wraps `cyclePosition` back to `0` and advances `currentWeek` (`% weeks.length`, so finishing the last week's last day cycles back to week 0, week type `"build"`, and the wave restarts indefinitely rather than the program simply ending).

### Saved workout templates

`WorkoutTemplate` (`lib/gym/types.ts`) is a named, reusable snapshot of an already-generated plan — `{id, name, plan, duration_minutes, target_muscles}` — stored in `GymState.workoutTemplates`, mirroring the existing `MealTemplate` pattern (`store.tsx`'s `saveWorkoutTemplate`/`deleteWorkoutTemplate` prepend/filter the array exactly like `saveMealTemplate`/`deleteMealTemplate` do). Unlike the generator (which reshuffles within constraints every time) or "Repeat last workout" (tied to a specific past session), a template is a deliberately-named plan the user chose to keep exactly as generated, independent of both. `WorkoutTemplatesSheet.tsx` is a dual-mode `BottomSheet` mirroring `WeeklyPlanSheet`'s mode-switching: passed a `draft` (the current generated `plan` plus its duration/target muscles) it shows a name-and-save form; otherwise it lists saved templates with Start/Delete per row. `index.tsx` wires both directions into the same sheet instance (`open={templatesOpen || savingTemplate}`, `draft` only populated in the saving case) rather than mounting two sheets, keeping with the app's established one-overlay-at-a-time convention. A "Save" button next to the plan header (visible whenever a plan exists, alongside the "Your plan · ~N min · N exercises" summary) opens the save form; a "Saved templates" chip row (visible whenever any exist, positioned between the weekly-plan/program card and the "Recommended today" nudge) lists up to 6 by name with a "Manage" chip opening the full list. Starting a template (`startTemplate()`, mirroring `repeat()`'s shape) calls `startWorkout` with the template's exact plan/duration/muscles untouched — no `fromScheduledDay`/`fromProgramDay`, since starting a saved template isn't following either schedule.

### Light/dark/system color scheme

The app was dark-mode only until a Settings toggle (`ColorSchemePicker.tsx`, in the "Appearance" section alongside `ThemePicker`) added light mode and system-following. `GymState.colorScheme` (`lib/gym/types.ts`'s `ColorScheme` — `"system" | "light" | "dark"`) defaults to `"dark"`, not `"system"`, deliberately: the app had exactly one look until now, so a silent flip to light for anyone whose device happens to already be in light mode would be a bigger surprise than just adding the option and leaving existing behavior as the default for everyone already using the app.

`styles.css`'s `:root` block still holds the original dark values unchanged (also the values active before hydration, and the ones `RootShell`'s hardcoded `class="dark"` was always describing). A new unlayered `.light { ... }` class, applied via a `GymProvider` effect that mirrors the existing accent-class effect exactly (toggling `.dark`/`.light` on `<html>` based on `state.colorScheme`, resolving `"system"` via `window.matchMedia("(prefers-color-scheme: dark)")` and updating live via that query's `change` listener — no reload needed if the OS setting flips while the app is open), overrides only the *structural/neutral* tokens: `--background`, `--foreground`, `--card`/`--card-foreground`, `--popover`/`--popover-foreground`, `--surface`/`--surface-strong`, `--secondary`, `--muted`/`--muted-foreground`, `--accent`/`--accent-foreground`, `--destructive`/`--destructive-foreground`, `--border`, `--input`, `--shadow-float`, and `color-scheme` itself. Every accent's own `--primary`/`--primary-foreground` pair is left untouched and reused identically in both modes — those are self-contained on a solid `bg-primary` surface (a button, a filled badge) and were already chosen for contrast against their *own* background, not the page's, so they need no light-mode equivalent. `--background` in `.light` is a soft off-white (`oklch(0.97 0.002 260)`) rather than pure white, matching iOS's own light "systemGroupedBackground" rather than a stark white — `.glass`/`.glass-strong` read as translucent white panels floating on that, the light-mode equivalent of the dark theme's translucent dark-gray-on-black panels. `.glass-header` (`Screen.tsx`'s sticky header backdrop — see its own paragraph below) originally hardcoded a literal `oklch(0 0 0 / 55%)` black tint, which would have read as a stray black bar over a light-mode page; it now derives its tint from `--background` via `color-mix` instead, so it follows whichever mode is active — see that paragraph for the mechanism.

This SSR/hydration handoff has the same accepted, undocumented-until-now gap the accent-color system already lived with before this feature: `RootShell` has no access to the stored `colorScheme` at request time, so every cold load paints dark first (`.dark`'s values, via `:root`'s own baseline) and only switches to `.light` client-side once `GymProvider`'s effect runs post-hydration — a possible one-frame flash of the wrong theme on a light-mode device, not solved here. `SplashScreen` in particular always renders in its original dark colors on every cold launch regardless of the chosen scheme, since it's gone (or is finishing its exit fade) by the time hydration corrects the class — treated as acceptable, branded, always-dark-splash behavior rather than a bug to chase.

Two things were deliberately left alone as part of this change: `BarcodeScanner.tsx`'s full-screen camera overlay keeps its hardcoded `bg-black`/`text-white` styling — a camera viewfinder's chrome is conventionally always-dark regardless of system theme, the same "content-intrinsic color, not theme-following" reasoning already applied to `SplashScreen`'s sparks, `Confetti`'s palette, and `WaterTile`'s fixed-blue badge icon elsewhere in this doc. And a few remaining hardcoded `text-white/[…]` ghost-watermark opacities on `index.tsx`'s Home tiles were switched to `text-foreground/[…]` so they read correctly in both modes, rather than always assuming a black background.

`Screen.tsx`'s sticky page header uses its own `.glass-header` instead of `.glass-strong` — reported as looking like a visibly different-colored "gray bar" sitting on top of the page, unlike `index.tsx`'s Home header (plain title text straight on `--background`, no panel at all). The difference was `--surface-strong` itself: a genuinely lighter, desaturated gray (`oklch(0.3 ...)`), not a tinted background color, plus `.glass-strong`'s own 1px border. `.glass-header` keeps the same backdrop-filter blur — still needed so header text stays legible over whatever's scrolled underneath it, the reason any of this has a blur layer at all — but tints with `color-mix(in oklch, var(--background) 55%, transparent)` (the page's own background, made translucent — derived at runtime rather than a literal oklch value, since `--background` itself has no alpha channel to soften; the same technique `.accent-custom`'s own `--ring`/`--glow-primary` already used) instead of `--surface-strong`, and drops the border entirely, so it reads as the page's own background rather than a separate surface layered on top of it. Scoped to `Screen.tsx` only, not a change to `.glass-strong` itself, which stays as-is for the tab bar pill, `BottomSheet`, `UpdateBanner` and the rest of its call sites — those are genuinely separate surfaces (a sheet, a floating pill) where a visible panel is the correct read, unlike a page's own header. Deriving the tint from `--background` rather than a hardcoded black is also what makes this header correct in light mode — see the "Light/dark/system color scheme" section above.

`::selection` (in `@layer base`) is styled to `--color-primary`/`--color-primary-foreground` instead of the browser default, so text selection anywhere in the app — not just the inputs below — follows whichever accent is active, the same way `.glow` and every `bg-primary` already do.

**A `--background`/`--foreground`-based knob or icon color breaks once `--background` can be near-white too.** A follow-up bug report — the Supersets toggle on `generate.tsx` rendering as a black knob in light mode — traced to a pattern that was silently correct for as long as the app was dark-only and stopped being correct the moment `.light` existed: several small controls painted themselves in `bg-foreground`/`text-background` specifically *because* those tokens always resolved to white/black respectively, not because "always white" or "always black" was actually the intent. Once `--background`/`--foreground` could also resolve to the `.light` palette's near-white/near-black pair, every one of these flipped color along with the rest of the page, which is wrong for a surface that isn't itself theme-relative:

- `generate.tsx`'s Supersets `role="switch"` knob used `bg-foreground` for its thumb — white in dark mode (legible against both the green "on" track and the gray "off" one), but black in light mode, reading as a broken/wrong-color toggle sitting on top of a bright green track. iOS's own switch knob is always a plain white circle regardless of system theme or the track's own color; fixed to `bg-white` with a small drop shadow (`shadow-[0_1px_3px_oklch(0_0_0/35%)]`) for definition against the light theme's own light-gray "off" track, where a plain white knob would otherwise have too little contrast against `--secondary`. A deliberate, content-intrinsic exception to "never hardcode colors," same category as `BarcodeScanner`'s always-dark camera chrome above — a switch knob's white isn't following the page's theme, it's following the platform's own switch convention.
- `ThemePicker.tsx`'s selected-accent checkmark used `text-background` on top of each accent's own fixed swatch color (`a.swatch`, a literal oklch matching that accent's `--primary`) — reliably a *dark* check as long as `--background` was always black, which read fine against every swatch (even the brightest, green/yellow). Once `--background` could be near-white, the same checkmark went from a legible dark mark to a near-invisible near-white one, specifically on the two brightest swatches (green, yellow) where a light check on an already-light swatch nearly disappears. Fixed by scoping each swatch button with its own `accent-${a.id}` class (the exact class `GymProvider`'s effect already applies globally to `<html>`, reused here locally — CSS custom properties cascade to whatever element declares them, not just `<html>`) and swapping the checkmark to `text-primary-foreground`: each swatch's own already-tuned, mode-independent foreground pairing (dark for green/orange/yellow, white for blue/purple/pink/custom — see the `.accent-*` blocks) rather than a value that happened to always be dark only because `--background` used to always be black.
- `AvatarPicker.tsx`'s per-avatar icon had the identical bug, one level less fixable the same way: its six avatar circles (`AVATARS` in `lib/gym/avatars.ts`) are fixed brand colors with no matching `accent-*` CSS class to borrow a foreground from, so each `AvatarOption` gained its own explicit `ink` field — a fixed oklch chosen for contrast against that avatar's own `bg`, picked with the same "bright bg needs dark ink, darker/saturated bg needs light ink" logic already used for the six accents (`panda`'s bright green and `cat`'s bright orange get dark ink; the rest get white), applied via inline `style={{ color: a.ink }}` rather than a `text-*` class. The selected-avatar checkmark *badge* (the small circle overlaid bottom-right, still `bg-foreground`/`text-background`) was deliberately left alone — it's self-consistently paired (both tokens flip together and stay legible against each other, since the badge is judged against its own fill, not a fixed swatch underneath it), so it was never actually broken by light mode the way the swatch-colored icon and checkmark above were.

The general rule this settled on: `bg-foreground`/`text-background` (or the reverse) is only correct for a surface that's *supposed* to track the page's own light/dark state — body text, a themed panel. The moment a color is compared against something with its own fixed identity (an accent swatch, an avatar's brand color, a platform-convention switch knob), reach for that thing's own paired foreground token (`text-primary-foreground` scoped to the right `accent-*` class) or, if no such pairing exists yet, add one explicitly (`avatars.ts`'s `ink`) rather than borrowing `--background`/`--foreground` for the coincidence of it currently having the right value.

**The real iOS status bar (not page content) had the identical bug, one layer further out — and needed a fundamentally different fix than the page's own SSR/hydration gap.** A report with a screenshot showed the actual OS status bar — the native time/signal/battery row above the page, not anything `Screen.tsx` or `TabBar.tsx` render — staying solid black in light mode. `__root.tsx`'s `head()` SSRs two meta tags that control this on an installed iOS PWA: `apple-mobile-web-app-status-bar-style` (`"black"` = opaque black bar with white icons, `"default"` = white bar with black icons — no third option gives light-bar/light-icons or a value that tracks the page, only these two fixed pairings) and `theme-color`, both hardcoded dark for the app's original dark-only design.

A first attempt mirrored the already-accepted `<html class="dark">` pattern: a `GymProvider` effect flipping these two meta tags' live `content` via `document.querySelector`+`setAttribute` post-hydration, same tradeoff as the class (a cold launch starts dark, corrects once JS runs). That's not sufficient here, confirmed by a follow-up report that force-quitting and reopening the installed PWA *still* showed black: `apple-mobile-web-app-status-bar-style` is read by iOS straight from the SSR'd HTML at cold-launch time, *before* any of this JS has had a chance to run — and since `__root.tsx`'s `head()` had no way to know the user's preference at request time, it served the identical hardcoded dark value on literally every launch, forever. A client-only fix structurally cannot reach back and change what iOS already read from that specific response; the `<html>` class's "corrects after hydration" story only works because the *page's own* paint happens after hydration too, which isn't true of a value iOS consults before handing off to the page at all.

The real fix needed the *server* to know the preference, which meant a cookie (the one piece of this preference an HTTP request can actually carry), not just `localStorage`:

- `GymProvider`'s color-scheme effect (`store.tsx`) now also writes `forge-color-scheme=dark|light` to `document.cookie` (1yr expiry) every time it resolves the scheme — alongside the existing `document.querySelector`+`setAttribute` DOM updates, which still matter for a same-session live correction (flipping "system" mode when the OS setting changes, or immediately after picking a scheme in Settings, without waiting for a reload).
- `__root.tsx`'s `head()` is `async` and reads that cookie via a small `getColorSchemeCookie` helper — `createIsomorphicFn().server(readColorSchemeCookie).client(...)`, since `head()` runs both server-side (the real SSR) *and* client-side (TanStack Router re-invokes a route's `head()` on client-side navigation, to keep `<HeadContent/>` in sync without a reload). The server half calls `@tanstack/react-start/server`'s `getCookie()`, kept in its own `src/lib/colorSchemeCookie.server.ts` file — `__root.tsx` itself is bundled for the client too (it hydrates `RootComponent`), and `@tanstack/react-start/server` is a genuinely server-only import that fails the build ("Import denied in client environment") if pulled into any file the client bundle touches. The client half just reads `document.cookie` directly, needing no framework API at all for a value written by this same origin's own JS.
- Missing cookie (a first-ever visit, or any client from before this shipped) defaults to dark, matching the app's original, only-ever-shipped look — the same reasoning `colorScheme`'s own `"dark"` default already uses.

This part alone isn't sufficient either, on its own: caching. `src/server.ts`'s `withDocumentCaching` used to treat the whole document response as safe to cache aggressively (`public, max-age=3600`) on the reasoning that it embedded no per-request data — no longer true once `head()` reads a cookie. The obvious fix, `Vary: Cookie`, turned out not to be reliable: testing (a plain `fetch()` from Node working correctly on every request, while the identical request via Playwright's Chromium kept replaying a document cached from an earlier, cookie-less request) showed Chromium's disk cache doesn't consistently honor `Vary: Cookie` in practice. Since that first, cookie-less response is also a one-time event per browser (the cookie gets written the moment `GymProvider`'s effect first runs, so nearly every request after a user's actual first visit carries it), the only fully reliable fix was to stop the browser from caching this document at all: `withDocumentCaching` now sets `Cache-Control: no-store` unconditionally, dropping the long-lived-caching branch entirely rather than trying to make an unreliable cache correctly key on a cookie.

That still wasn't the whole story — `public/sw.js`'s own `PAGES_CACHE` (its stale-while-revalidate handling of navigations, see the section below) is a second, independent caching layer, entirely unaffected by `Cache-Control` (a service worker's `cache.put()` is plain code, not something that consults response caching headers at all). An attempted fix there — skip the cache when `request.headers.get("cookie")` shows this cookie — looked correct in isolated testing (blocking the service worker entirely made the bug go away) but turned out to be silently dead code: `Cookie` is one of the Fetch spec's *forbidden* header names, redacted from `request.headers` in every context including a service worker's `fetch` event, even though the browser still attaches the real cookie to the actual network request underneath. There is no spec-legal way for `sw.js` to read it. Reverted to the SW's original, unconditional stale-while-revalidate logic, with the limitation now documented in place rather than a check that only looked like it worked: switching color scheme can leave one stale launch behind if `sw.js` already had `/` cached from before the switch, self-correcting from the *next* launch onward, since the background revalidation fetch that stale-while-revalidate always runs (regardless of cache hit/miss) still gets the current, correct cookie's response and overwrites the cache with it — confirmed via Playwright across two consecutive simulated relaunches (first stale, second correct). Bounded, self-correcting staleness, not the original bug's indefinite stuck-black — the practical ceiling on how well this can work while iOS reads a launch-time meta tag from HTML a service worker is allowed to cache, but not allowed to see the one header that would tell it that cache is stale.

**None of the above was actually the (whole) fix, because the underlying assumption behind all of it turned out to be wrong.** Every layer above got proven correct in isolation — direct `curl`/Node `fetch()` against the deployed server confirmed the exact right `apple-mobile-web-app-status-bar-style`/`theme-color` values for a light-mode cookie, on demand, past every cache layer — and yet the status bar stayed black on the user's real device (iOS 27.0) even after a full `Settings → Safari → Advanced → Website Data` wipe (which does clear the service worker/Cache Storage/cookies, unlike merely deleting and re-adding the Home Screen icon, which does **not** touch any of that underlying site storage). With the server-response layer exhaustively eliminated as a variable, the remaining explanation was that the mechanism itself had changed: iOS 26+'s "Liquid Glass" redesign (per contemporaneous reports, as of September 2026) no longer reliably honors `apple-mobile-web-app-status-bar-style`/`theme-color` for an installed PWA's status bar tint at all — instead it samples the actual rendered page background near the top of the viewport. `RootShell`'s `<html>`/`<body>` background (and, during the cold-launch window, `#forge-boot`'s own background sitting on top of it) had been unconditionally black this whole time, same as the meta tags used to be — so fixing the meta tags alone could never have shown up as a visible fix on this iOS version regardless of how correct they were.

The fix: `RootShell` now reads the same `forge-color-scheme` cookie `head()` already reads (via the same `getColorSchemeCookie()` isomorphic function, so server and client resolve identically and hydration can't mismatch) and uses it to pick `<html>`'s class (`dark`/`light`, previously hardcoded `"dark"`) and both inline-CSS background colors — `html,body` and `#forge-boot` — between `#000` and `#f2f2f7` (a plain hex approximation of `.light`'s `oklch(0.97 0.002 260)`, since the critical inline `<style>` has no oklch fallback to lean on and needs to match before `styles.css` has even loaded). `head()`'s own `color-scheme` meta tag, previously also hardcoded `"dark"`, was made cookie-conditional the same way for consistency with `RootShell`'s inline copy of the same property. This is a genuinely different fix from the cookie/caching work above, not a rehash of it: that work was about getting the *meta tags* correct past every caching layer, which turned out to be necessary but not sufficient, since iOS 26+ mostly stopped consulting those tags for this purpose — this part is about making the thing iOS 26+ actually samples (the SSR'd page background itself) correct at the same request-time granularity. Confirmed fixed on a real iOS 27 device: force-quitting and reopening the installed PWA now shows the correct status bar for whichever scheme is active.

**That confirmation came with a caveat: switching the scheme in Settings needed an explicit "Force update" (`pwa.ts`'s `forceUpdate()`) to actually take, rather than a plain force-quit + reopen — worse than the "one stale launch, self-corrects next" bound the `PAGES_CACHE` section above documents.** The reason: that bound assumes the *following* launch's own background revalidation fetch reliably finishes and overwrites the cache before iOS evicts the service worker, which in practice it doesn't always manage to do — `forceUpdate()` masked this by wiping Cache Storage outright, which is a much bigger hammer than the actual problem needs. The real gap: switching `colorScheme` in Settings happens via a client-side effect, not a navigation, so `sw.js`'s stale-while-revalidate handler (which only runs on an actual `request.mode === "navigate"` fetch event) never gets a chance to refresh `PAGES_CACHE`'s `/` entry at the moment of the switch — that entry just sits there holding the old scheme's HTML until some future navigation happens to trigger a refresh, if it manages to complete in time at all.

Fixed by having the switch push the refresh itself instead of waiting for one to happen to occur: `store.tsx`'s color-scheme effect now tracks the last resolved dark/light value in a `lastAppliedDarkRef`, and on a genuine change (not the initial mount, which just reflects whatever the cookie/SSR already had) posts `{ type: "forge:revalidate-shell" }` to `navigator.serviceWorker.controller`. `sw.js` gained a matching `message` listener that refetches `/` (`cache: "reload"`, bypassing the browser's own HTTP cache too) and overwrites `PAGES_CACHE`'s entry for it — the same fetch-and-`cache.put` the navigate handler already does, just triggered immediately by the switch itself rather than by the next navigation. Because this runs while the page (and its controlling service worker) are certainly still alive — the user is mid-interaction with the Settings screen — it doesn't have the eviction-race problem a launch-triggered revalidation does. By the time the user actually force-quits and reopens, the cache is already correct; there's no stale launch to wait out at all.

**That still only fixes the NEXT reopen — the ask afterward was for the switch to take effect immediately, without the user having to manually force-quit at all.** The classList toggle already repaints the page's own content live; the gap is specifically the native OS status bar chrome, which doesn't follow it, and there's no public WebKit API to ask it to resample mid-session. A first attempt tried nudging it indirectly — a speculative invisible 1px scroll-and-back, on the theory that Liquid Glass's materials react to scroll position — deployed and confirmed by the user NOT to work in practice; that scroll-nudge code has since been removed. The only checkpoint that's actually *confirmed* to make Liquid Glass resample correctly is a fresh load — that's exactly what force-quit + reopen is, and it's already been confirmed to work.

So `applyScheme`'s post-switch step now does the closest thing a running page can do to reopening itself: it calls `location.reload()` automatically right after a genuine switch — architecturally the same "fresh load of /" a force-quit + reopen already produces, just triggered from live JS instead of the OS. No workout or nutrition data is at risk: `GymState` is already flushed to `localStorage` synchronously by the persistence effect above this one on every change, and the switch only ever happens from the Settings screen, never mid-workout. An immediate `location.reload()` right after posting `forge:revalidate-shell`, though, would still race that cache write — the reload could hit `PAGES_CACHE`'s cache-first branch before the SW's own `fetch`/`cache.put` finishes, serving the OLD scheme's shell one more time despite the fix being "in flight." So the reload waits for it: the client opens a `MessageChannel`, passes `port2` along with the revalidate-shell message, and only reloads once `sw.js` posts a reply back over `port1` — `sw.js`'s handler now replies (via `event.ports[0]`) once its `cache.put` settles, success or failure alike, rather than the client guessing a fixed delay. A 1.5s `setTimeout` safety net reloads anyway if the SW never replies (offline, or no controller yet on a page's very first-ever load, where there's nothing cached to race in the first place) — a switch should never fail to reload just because the revalidation stalled.

This is a real page reload, not another unverified guess — it hits the exact load-time checkpoint already proven to retint the status bar correctly (force-quit + reopen), so confidence here is meaningfully higher than the scroll-nudge attempt was. It hasn't been re-confirmed on a real device as of this writing that a same-session, JS-triggered `location.reload()` of an installed standalone PWA is treated identically to an OS-driven relaunch by Liquid Glass specifically — there's no strong reason to expect WebKit to distinguish them, since both are the same navigation lifecycle from its perspective, but it's still an inference from the confirmed force-quit case rather than something tested in exactly this form.

### Internationalization (English/Dutch)

The app shipped English-only until a Settings toggle (`LanguagePicker.tsx`, in "Appearance" directly below `ThemePicker`, mirroring `ColorSchemePicker`'s own grid-of-options pattern) added Dutch. `GymState.language` (`lib/gym/types.ts`'s `Language` — `"en" | "nl"`) defaults to `"en"` for the same reason `colorScheme` defaults to `"dark"` and not `"system"`: the app only ever shipped in English, so silently switching for anyone whose OS happens to be set to Dutch would be a bigger surprise than just adding the option and leaving existing behavior as the default for everyone already using the app.

**Scope: UI chrome only, not the exercise/muscle domain content.** `lib/gym/i18n.ts` translates navigation, screen titles, buttons, form labels, empty states, toasts, and dynamic sentences built from the app's own copy — everything the app itself says. It deliberately does **not** translate: exercise names/instructions/cues (`lib/gym/data.ts`, 350+ entries — a genuinely separate, much larger undertaking from translating the app's chrome, and lifters commonly know these terms in English regardless of app language); `Muscle`/`TargetMuscle`/`EquipmentId` labels; `SPLIT_TEMPLATES`/`PROGRAM_PRESETS` labels and descriptions (`lib/gym/splits.ts`/`programs.ts` — training-methodology names like "Push / Pull / Legs" or "Upper / Lower" that read the same way muscle-group terms do); `ThemePicker`'s accent color names ("Electric Green", "Ocean Blue" — decorative brand-style names, not functional UI text); or user-entered content (profile names, avatar labels, a saved template's own name). This boundary was an explicit user decision (asked via a scoped clarifying question before starting, given the scale difference between translating ~9,500 lines of UI chrome versus also translating a 350+ entry exercise database) — a future request to extend translation into the exercise catalog is a distinct, much larger project from this one.

**Architecture.** `lib/gym/i18n.ts` exports one `en` object — a single nested literal, namespaced by screen/component (`home`, `settings`, `generate`, `session`, `history`, `nutrition`, `exercises`, `equipment`, `addFood`, `auth`, `createMeal`, `createRecipe`, `nutritionGoals`, `nutritionQuestionnaire`, `programBuilder`, `weeklyPlan`, `workoutTemplates`, `swapSheet`, `bottomSheet`, `updateBanner`, `plateHint`, `streakCalendar`, `barcodeScanner`, `readiness`, `progression`, `mealTypes`, `nutrients`, `activityLevels`, plus a shared `common` namespace for cross-cutting strings like Save/Cancel/Done and a `dow` day-of-week array) — and an `nl` object typed exactly as `typeof en` via `const nl: Dict = { ... }`, so a missing or mistyped Dutch key is a compile error, not a silent runtime fallback to English. Static strings are plain values; anything that needs interpolation (a count, a name, a computed sentence like "Superset · {rounds} rounds") is a function value with the same signature in both languages, e.g. `home.weekOf: (n: number, m: number, deload: boolean) => string`. This is deliberately a hand-rolled object literal rather than an i18n library (no `react-intl`/`i18next`) — the app has no build step for extracting/compiling message catalogs, and a plain typed object gives full autocomplete plus a compiler-enforced guarantee that every English key has a Dutch counterpart, which a string-keyed `t("some.key")` lookup function can't provide.

`useTranslation()` reads `state.language` via `useGym()` and returns the matching dictionary object (`DICTS[language]`, a stable module-level reference per language — not rebuilt every render, which matters for effects that legitimately depend on it, e.g. `BarcodeScanner`'s camera-setup effect includes `t` in its dependency array specifically so a language switch mid-scan re-renders its error copy without needlessly restarting the camera on every unrelated render). Every component that renders translated text calls `const t = useTranslation();` and reads `t.<namespace>.<key>` — there's no context wrapper or prop-drilling, since `useGym()` is already globally available the same way every other piece of app state is. `useLocale()` similarly returns a BCP-47 locale string (`LOCALE: Record<Language, string>`, `"en-US"`/`"nl-NL"`) for the handful of `toLocaleDateString`/`toLocaleString` call sites (date labels on Home, History, session summaries, the streak calendar's day tooltips) — passing this instead of `undefined` (the previous, device-locale-following default) means weekday/month names read in the same language as the rest of the UI once a user picks one, rather than silently continuing to follow whatever the OS itself happens to be set to.

**Two lib files needed light surgery to carry translated copy out of pure, non-React functions.** `lib/gym/progression.ts`'s `suggestWeight()` used to hardcode its `reason` strings ("You hit 12+ reps on every set last time…") directly; it now takes an optional 6th `copy: ProgressionCopy` parameter (an interface of the handful of strings/templates it needs), defaulting to a module-level English constant so any caller that doesn't pass one still works, with all three real call sites (`generate.tsx`, `session.tsx` ×2) now passing `t.progression`. `lib/gym/readiness.ts` similarly used to return the finished English sentence from `readinessNote()`; it now exports `readinessNoteKind()` — a `"trimmedLot" | "trimmedLittle" | "nudgedUp" | null` discriminant rather than text — and the one call site (inside `progression.ts`) maps that kind to `copy.noteTrimmedLot` etc. `READINESS_LABELS` (previously `{emoji, label}` per score) is now `READINESS_EMOJI` (emoji only); the English/Dutch label text moved to `i18n.ts`'s `readiness` namespace, keyed 1-5 to match. Neither lib file imports React or `useTranslation` — they stay plain, testable functions that take translated strings as data, the same shape the rest of the codebase's `lib/gym/*` files already have.

**Verification.** Confirmed via Playwright (not just tsc/eslint) that switching languages in Settings actually re-renders every screen correctly and that the choice persists across full page navigations (seeding `forge.gym.state.v2`'s `language` field directly in `localStorage`, then a real `page.goto()` per route, waiting out the splash screen's ~2.5-2.8s minimum visible time before asserting): Home, Workout/generate, Nutrition, History, Exercises, Equipment, and Settings itself all render correctly in Dutch, and switching back to English from the Dutch UI (clicking the "English" option while `LanguagePicker`'s own labels are themselves in Dutch) works too. One real, expected side effect of translation, not a bug: Home's hero card title ("Klaar om te trainen?" vs "Ready to train?") is long enough in Dutch to hit the card's existing `truncate` class where the English string didn't — this is the same graceful-degradation `truncate` already handles for long exercise names elsewhere in the app, working as designed once a translation happens to be longer, not a new failure mode introduced by this feature.

### Editable value fields select-on-focus

`lib/gym/numericInput.ts`'s `selectOnFocus` (an `onFocus` handler) selects a text/decimal input's entire current value the moment it's focused, so tapping into a field that already holds something — a prefilled weight, rep count, calorie goal, duration, plate count, a food name pulled in from a label scan — lets the user immediately start typing to replace it, rather than having to delete the old value character-by-character first. Combined with the `::selection` theming above, the highlight itself reads as an intentional "this is about to be overwritten" cue in the app's own accent color rather than the operating system's generic (and pale, easy-to-miss-on-iOS) selection blue. Applied to every `type="text"` value field in the app that's prefilled or re-editable in place — `session.tsx`'s weight/reps inputs, `generate.tsx`'s custom-duration field, `equipment.tsx`'s plate-count fields, and the various sheets' numeric fields (`AddFoodSheet`, `NutritionGoalsSheet`, `NutritionQuestionnaireSheet`, `CreateMealSheet`) — all of which already used `type="text"` + `inputMode="decimal"|"numeric"` rather than `type="number"` for the `DECIMAL_INPUT_RE` comma-or-period parsing `type="number"` can't support (see `parseDecimal`, same file).

`selectOnFocus` defers the actual `input.select()` call to a `requestAnimationFrame`, for the same reason the function it replaced (`placeCursorAtEnd`, which positioned the cursor at the end instead of selecting) had to: a tap/click both focuses the input *and* positions the cursor/selection at the click point, but that native positioning happens on `mouseup`, which fires *after* the `focus` event this handler runs on. Selecting synchronously in the focus handler would just get silently overwritten a moment later by the browser's own click-positioned (zero-length) selection — deferring one frame runs after that's already happened, so this handler's `select()` applies last and actually sticks.

### Imports

`@/*` resolves to `./src/*` (from `tsconfig.json`, wired up by the pre-bundled Vite config — see above). Usage is inconsistent in the existing code — `components/ui/*` and `lib/gym/catalog.ts` use `@/...`, while `routes/*` and `components/gym/*` mostly use relative imports. Either works; match the surrounding file's style.
